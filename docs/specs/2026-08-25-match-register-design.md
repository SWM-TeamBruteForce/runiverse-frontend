# 예약 매칭 등록 설계

2026-08-25 · 대상 화면 S08 · 기능정의서 `MATCH-REGISTER-001`

이 문서는 **무엇을 왜 그렇게 정했는지**만 적는다.
설계만 하고 구현은 미뤘다 — 1인 러닝을 먼저 만들기로 했다.

---

## 1. 범위

매칭 조건을 골라 서버에 신청하는 화면 하나와, 그 앞에 서는 위치 권한 시트.

**넣는 것**

- S08 매칭 등록 — 시간 슬롯 · 목표 거리 · 등록 CTA
- 시간 선택 시트 — 슬롯별 대기 인원
- 위치 권한 시트 (최초 1회)
- 등록 실패 네 갈래

**빼는 것**

| 뺀 것 | 이유 |
|---|---|
| SSE 매칭 상태 구독 | 새 인프라다. 다음 조각 |
| 글로벌 스티키 배너 | 상태 구독이 있어야 그릴 것이 생긴다 |
| 로비 S10 · 파티원 | 매칭이 확정돼야 닿는 화면 |
| 시그니처 컬러 확인 줄 | 2-4 참고 |
| 알림 권한 | 2-3 참고 |

### 서버가 아직 없다

| 엔드포인트 | BE 현황 |
|---|---|
| `POST /api/v1/running-matches` (11번) | **개발전** |
| `GET /api/v1/running-matches/slots` (14번) | **개발전** |

명세는 확정돼 있어 앱은 만들 수 있지만 **실기기 확인은 서버가 생긴 뒤에야 가능하다.**
`FakeMatchRepository`로 화면과 상태 전이를 검증하고, 서버가 오면 구현체만 갈아끼운다.

## 2. 결정

### 2-1. ⚠️ 앱이 날짜를 조립하지 않는다

가장 중요한 결정이다.

슬롯 API가 `scheduledStartAt`을 **완전한 DateTime**으로 준다(`2026-07-25T19:00:00` —
KST 기준, 오프셋 없이 초 단위까지). 등록할 때 **받은 값을 그대로 되돌려 보낸다.**

앱이 "오늘 + 19:00"을 조립하면 자정 근처나 기기 시계가 어긋났을 때 엉뚱한 날짜가 나간다.
서버가 준 문자열을 그대로 쓰면 그 위험이 없고, 무엇이 유효한 슬롯인지 판단하는 주체도
서버 하나로 남는다.

### 2-2. 마감된 슬롯은 지우지 않고 잠근다

명세의 `selectable: false`가 그런 뜻이다. 목록에서 빼면 "18:00이 왜 없지"가 되고,
시간이 흐르며 목록이 줄어드는 것도 이상하게 읽힌다. 남기되 눌리지 않게 한다.

`waitingCount`는 사회적 증거다. 대기 인원이 많은 슬롯으로 유도해 매칭 성사율을 올리는
장치라 빼면 안 된다(`implementation-notes.md` 2-1).

### 2-3. 위치만 묻는다. 알림은 나중이다

정본 권한 시트에는 위치와 알림이 나란히 있다. **알림은 빼기로 했다** —
받아도 보낼 채널(FCM)이 없어 쓸 데가 없고, 권한만 먼저 받아두면 사용자에게 손해다.
FCM을 붙일 때 그 자리에서 묻는다.

위치는 `geolocator`가 이미 있어 패키지를 더하지 않는다.

**시트를 봤는지 따로 저장하지 않는다.** `Geolocator.checkPermission()`이
`denied`(아직 안 물음)일 때만 띄우고, 이미 허용했거나 영구 거부한 사람에게는 건너뛴다.
저장소를 만들면 그 값과 실제 권한 상태가 어긋날 수 있다.

**거부해도 등록은 진행한다.** 예약 매칭에 위치가 필요한 시점은 러닝을 시작할 때다.
여기서 막으면 등록 자체를 못 하게 된다.

### 2-4. 시그니처 컬러 확인 줄을 뺀다 `[정본 이탈]`

정본 S08에는 `오늘 가져갈 내 색 · 코발트 블루 [변경]` 줄이 있고,
`implementation-notes.md`는 그 자리를 이렇게 설명한다 —
*"색이 실제로 의미를 갖는 순간이 여기여서, 프로필에만 두면 대부분 기본값으로 매칭하게 된다."*

**그런데 색을 모으는 기능이 아직 없다.** `SignatureColorRow`는 지금 "아직 색을
모으지 않았어요" 문구만 그린다. 확인할 색도, 바꿀 셰이드도 없는 자리에 줄을 두면
고장 난 것으로 읽힌다. 프로필 헤더에서 컬러 밴드를 뺀 것과 같은 이유다.

> ⚠️ **팀 확인이 필요하다.** 색 기능이 생기면 반드시 되살려야 하는 줄이다.

### 2-5. 네트워크 오류에 재시도를 붙이지 않는다

기능정의서 예외 11이 명시한다 — 네트워크가 끊기면 **등록됐는지 알 수 없다.**
그 상태에서 다시 보내면 중복 신청이 생긴다.

"확인 중"으로 두고, 현황 조회(`GET /api/v1/users/me/running-match`)로 확인하게 한다.
그 조회는 다음 조각에 속하므로, 이번 조각에서는 **재시도 버튼을 주지 않고** 홈으로 돌려보낸다.

## 3. 실패 네 갈래

| 응답 | 화면 |
|---|---|
| `409 ALREADY_MATCHING` | "이미 진행 중인 매칭이 있어요" · 등록 화면을 닫는다 |
| `409 MATCH_COOLDOWN` | `cooldownUntil`까지 신청할 수 없다고 시각과 함께 알린다 |
| `400` | ⚠️ 앱 규칙이 서버와 어긋났다는 신호. 앱이 고정 선택지만 보내므로 정상 경로에서는 나오지 않는다 |
| 네트워크 | 2-5 참고. 재시도하지 않는다 |

쿨다운은 확정 후 이탈(`MATCHED_LEFT_PENALTY`)과 러닝 중 조기 종료(`RUNNING_LEFT_PENALTY`)
둘 다에서 걸린다. 문구가 "이탈"만 말하면 러닝을 중간에 끝낸 사람이 이유를 모른다.

## 4. 구조

```
domain/
  match_slot.dart          시각 · 대기 인원 · 선택 가능 여부
  target_distance.dart     3 · 5 · 10km ↔ 3000 · 5000 · 10000m
  match_failure.dart
  match_repository.dart
data/
  http_match_repository.dart
  fake_match_repository.dart
presentation/
  match_register_page.dart      S08
  match_slot_sheet.dart         시간 선택
  location_permission_sheet.dart
  match_provider.dart
```

`targetDistanceKm`을 도메인에 두고 미터 변환은 data가 한다. 화면은 `3km`를 말하고
서버는 `3000`을 받는데, 그 변환이 화면에 흩어지면 한쪽만 고치는 사고가 난다.

진입점은 홈 히어로의 `매칭 시작` — 지금은 준비 중 안내로 끝난다.

## 5. 테스트

프로젝트 규칙대로 **순수 계산 로직과 상태 전이**만 본다.

- 리포지토리 — 슬롯 파싱, **서버가 준 시각을 그대로 되돌려 보내는지**, 409 두 갈래, 400
- 등록 화면 — 시간·거리를 둘 다 골라야 CTA가 열리는지, 409 분기가 화면을 어떻게 가르는지
- 슬롯 시트 — `selectable: false`가 눌리지 않는지, 대기 인원이 보이는지
- 권한 시트 — `denied`일 때만 뜨는지, 거부해도 등록이 진행되는지
