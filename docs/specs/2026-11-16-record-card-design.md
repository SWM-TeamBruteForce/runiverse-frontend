# 기록카드 설계

> 2026-11-16 · 브랜치 `feat/record-card`
>
> 시안 `MpJxkA7fPj6MJs5uL07CVb` `218:807`(기록카드 페이지 · 기록 만들기 · 상세)은
> **1차안이고 참고용이다.** 기획은 이 문서가 정본이다 — 사용자가 그렇게 정했다.

## 1. 무엇을, 왜

**기록카드는 끝난 러닝 하나에 유형·회고글·사진을 얹어 남기는 것이다.** 저장하면
AI가 회고와 러닝 지표, 사진으로 음악을 만든다(사용자가 켜고 끈다). 기록카드 탭은
월 캘린더로 모아 보고, 공개한 카드는 프로필에 그리드로 선다.

지금 기록카드 탭은 `ComingSoonPage`다. 온보딩 3장은 이미 "사진과 소감을 기록카드에
담고, 함께 달린 데이터로 만든 곡을 받아요"라고 약속하고 있고, **iOS는 심사 때문에
탭 자체를 숨겨 뒀다**(`app_shell.dart:27` `showRecordCardTab`).

기록 탭(S21)과 다르다. 기록 탭은 **숫자**를 본다 — 주간 막대, 오늘 낀 7일 스트립,
그날의 기록(달력 아이콘으로 월을 펼친다). 기록카드는 **그날의 경험**을 본다.

## 2. 목표 · 비목표 · 반목표

### 목표

- 기록카드 탭이 `ComingSoonPage`를 벗어난다.
- 러닝 요약(S15)에서 바로 카드를 쓸 수 있고, **방금 뛴 그 기록이 골라져 있다.**
- 카드 하나를 만들고, 고치고, 지운다.
- 캘린더가 월 ⇄ 분기 두 단계로 줄었다 늘었다 하고, 러닝 유형으로 거른다.
- **공개한 카드**(`PUBLIC`·`FRIENDS`)가 내 프로필과 남의 프로필에 그리드로 선다.
- 음악 생성을 켜고 끌 수 있고, 만들어지는 동안 무슨 일이 일어나는지 보인다.

### 비목표 (지금 안 만든다, 나중에 할 수 있다)

- **피드(S19).** 남들의 공개 카드를 모아 보는 타임라인은 없다. 공개 카드를 보는
  길은 그 사람 프로필뿐이다.
- **좋아요 · 댓글 · 신고 · 차단.** → iOS 되살리기와 얽힌다(10절).
- **음악 생성 파이프라인.** 앱은 상태를 읽고 재생만 한다.
- **실제 소리 재생.** 오디오 패키지가 `pubspec`에 없다. 이번엔 흉내까지다(8절).
- **영상 · 외부 공유 · 사진 순서 바꾸기.**
- **서버 연동.** 이번엔 전부 Fake다(5절).
- **연 단위 보기.** 월 조회밖에 없는 상태에서 연을 펴면 열두 번 부른다.

### 반목표 (이것이 되면 실패다)

- **안 뛴 날이 결손으로 읽히는 것.** 디자인 시스템 v1.1 §5-5가 잔디의 죄책감 문제를
  못 박았고 기록 탭도 그걸 지켰다. **`18/30` 같은 분수 표기를 쓰지 않는 이유**가
  이것이다(9절).
- **순위와 비교.** 누가 카드를 더 많이 썼는지, 누가 더 빨랐는지 보이지 않는다.
- **음악이 안 만들어졌다고 카드를 못 보는 것.** 카드와 음악은 따로다. 음악이
  실패해도 글과 사진은 그대로 있다. 백엔드 설계도 그렇게 적었다.
- **사진이 없으면 못 쓰는 것.** 사진은 선택이다. 회고글만으로 카드가 된다.
- **작성 세 화면을 넘나드는 동안 쓰던 것이 사라지는 것.** 앱을 죽였다 켠 뒤까지
  남기지는 않는다 — 그건 다른 약속이고, 이번엔 안 한다(7절).

## 3. 제약

### 프로젝트 규칙 (CLAUDE.md)

- 아이콘은 Lucide만. `Icons.*` 금지.
- `core/theme/tokens/` 밖에서 `Color(0x...)` 금지. 색·치수·타이포·문자열은 전부 토큰.
- `StateProvider` / `StateNotifierProvider` 금지. Riverpod 3.
- 화면은 **loading / data / error 3분기 필수**, **empty 상태와 다크·라이트 둘 다** 정의.
- UI 텍스트는 한국어.
- **한 PR 파일 20개 / 500줄 초과 금지.** → 다섯으로 쪼갠다(10절).
- 모든 flutter/dart 명령 앞에 `fvm`. 이 PC는 fvm이 PATH에 없어
  `.fvm\flutter_sdk\bin\flutter.bat`을 직접 부른다.

### "친구"라는 말

CLAUDE.md는 "친구라는 말은 쓰지 않는다(요청→수락 모델)"고 적었지만, **코드는 이미
`features/friend/`와 `user_friends_page.dart`를 두고 "친구 목록"이라 부른다.**
사용자가 공개범위를 `Friends`로 확정했으므로 이 문서는 그 결정을 따른다. CLAUDE.md
문구는 낡았다 — 고치는 것은 이 작업의 범위 밖이고, 별도로 제안한다.

### GPS 경로

CLAUDE.md의 "GPS 좌표·경로를 파티원에게 노출" 금지는 **달리는 중에 파티원에게 새는
것**을 막는 규칙이다(진행률과 격차만 공유).

기록카드의 경로 지도는 성격이 다르다. **내 러닝의 내 경로이고, 누가 보는지는 내가
공개범위로 직접 정한다.** 자동으로 새지 않는다. 그래도 `PUBLIC` 카드는 집이나 직장
근처가 드러날 수 있어, **공개범위를 고르는 자리에 경고 한 줄을 둔다**(9절).

### 경로는 **배경 없는 선 아트**다

기록카드의 경로는 지도 위에 긋지 않는다. **배경을 지우고 선만 남긴다** — 스트라바의
루트 아트와 같은 모양이다. 사용자가 정했다.

| | 그래서 |
|---|---|
| 프라이버시 | 배경이 없으면 그 선이 **어디인지 알기 어렵다.** 모양만 남고 장소는 지워진다 |
| 남의 카드 | 좌표만 있으면 그린다. `split-results`를 부를 필요가 없다 |
| 구현 | `CustomPainter` 하나다. **`flutter_naver_map`을 타지 않아** 키 없는 빌드 문제도, 페이저와 지도 제스처가 다투는 문제도 없다 |
| 캘린더 | 사진 없는 카드의 칸을 선으로 채운다. 그날 뛴 모양이 칸마다 달라 달력이 읽을 만해진다 |

진짜 지도가 보고 싶으면 **기록 탭 상세(S16)에 이미 있다.** 기록카드는 지도를 보는
화면이 아니라 그날을 남기는 화면이다.

### ⚠️ 그래서 **카드 응답이 경로·지표·파티원을 직접 실어야 한다**

카드가 `running_record_id`만 들고 러닝 쪽을 다시 부르는 길은 **막혀 있다.**

- `RunRecordRepository`에 기록 상세가 없다. `byRoom(runningRoomId)`뿐이고 주석이
  "기록 상세 API는 삭제됐다"고 적어 두었다.
- **`RunRecord.id ≠ runningRoomId`다.** 카드가 기록 ID만 들고 있으면 방 번호를 몰라
  아무것도 못 가져온다.
- 남의 카드는 **두 겹으로** 막힌다. 403(`NOT_ROOM_PLAYER` — 그 방의 참가자가 아니다)
  이고, 설령 403이 풀려도 명세가 `routes`를 "**이 구간의 본인 경로**"로 정의한다 —
  본인 기록이 없으면 **전부 `null`로 온다.** 남의 경로를 주는 API가 아니다.

그래서 카드 조회 응답이 아래를 직접 싣는다. **내 카드와 남의 카드가 같은 길을 탄다.**

- **정규화한 경로** — bounding box 기준 `0~1`. **절대 좌표가 앱에 한 번도 안
  내려온다.** 일시정지로 끊긴 조각별로 갈라서 준다
- **단순화한 점 수** — `split-results`는 10m마다라 5km면 수천 점이다. 선 아트에는
  200~300점이면 충분하다
- 총 거리 · 총 시간 · 평균 페이스
- 함께 뛴 러너 (닉네임 · 프로필 사진 · 색)

### 백엔드가 못 박은 것

노션 `기록 카드·AI 음악 DB 설계 공유`(2026-11-03)와 `AI 기능 아키텍처 및 data
입출력`(2026-11-13). **아직 실제 DB에 적용되지 않은 초안이다.**

| 사실 | 화면에 미치는 영향 |
|---|---|
| `unique(running_record_id)` — 러닝 기록 1건당 카드 **최대 1개** | 기록 고르는 목록에서 카드가 있는 기록은 **수정으로** 보낸다. 하루에 두 번 뛰면 **하루에 카드가 둘**일 수 있다 |
| `review_text` nullable | 서버는 빈 회고를 받는다. **필수는 앱만의 규칙이다** |
| `visibility in ('PUBLIC','FOLLOWERS','PRIVATE')` | 우리는 `FRIENDS`가 필요하다 → 협의 안건 |
| `activity` 컬럼에 **CHECK 제약이 없다** | 허용값은 스키마가 아니라 합의 사항이다 |
| 사진 장수 상한 없음 | 5장은 **우리가 정하는 값**이다 |
| `card_photo_key` 원본 하나. 썸네일 파생본 없음 | 캘린더 한 달 31칸, 분기 92칸이 원본이 된다 → 협의 안건 |
| 기본 음악 30초 + **사진 1장당 10초** | 사진 5장이면 6곡 |
| **상태는 묶음 하나에 하나** (`music_generations.status`). 전곡 성공해야 제공 | 곡별 상태가 없다. 1곡만 실패해도 카드 전체가 `FAILED`이고, 다시 만들기는 **전곡**이다 |
| 사진·캡션·회고·유형이 바뀌면 **전곡 재생성** | 수정 화면에 경고가 필요하다 |
| 생성 중 수정·삭제는 **활성 요청을 무효화**한다 | 생성 중에도 고치고 지울 수 있다. 경고만 한다 |
| SageMaker 처리 900초, 큐 대기 6시간 | "조금만 기다리세요"로 끝낼 수 없다 |
| 논리 삭제 컬럼 없음 | 삭제는 되돌릴 수 없다. 확인을 받는다 |

### 서버가 아직 없는 것

- **엔드포인트는 등록돼 있는데 본문이 비어 있다.** 3차 API 명세서의 `record-card`
  도메인에 여섯 줄이 있다 — 경로와 이름만이고 **요청·응답 스키마가 없다.** BE·FE
  현황도 안 찍혀 있다.

  ```
  POST   /api/v1/record-cards                            기록 카드 작성 요청
  POST   /api/v1/record-cards/drafts/{draftId}/complete  기록 카드 생성 확정
  GET    /api/v1/record-cards/{recordCardId}             카드 상세
  PATCH  /api/v1/record-cards/{recordCardId}             카드 수정
  DELETE /api/v1/record-cards/{recordCardId}             카드 삭제
  GET    /api/v1/users/{userId}/record-cards             기록 카드 모음
  ```

- **서버에 draft 개념이 있다.** 작성이 `POST /record-cards` → `drafts/{id}/complete`
  **두 단계**다. 사진을 그 사이에 올리라는 뜻으로 보인다. 이 문서의 `cardDraftProvider`는
  **앱 안에서만 도는 초안**이라 층위가 다르다 — 서버 draft를 언제 만드는지에 따라
  작성 흐름이 달라진다(10절 질문).
- **사진 업로드와 음악 관련 엔드포인트가 목록에 없다.** 생성 요청·재요청·상태 조회가
  어디에도 없다.
- **카드 모음이 `GET /users/{userId}/record-cards`다.** 사용자 단위이고, 캘린더가
  필요한 **월 조회를 어떻게 하는지(쿼리 파라미터·상한) 모른다.**
- **기록 목록 API(19번 `GET /users/me/running-records`)가 개발전이다.** 고를 러닝
  기록부터 가짜다 — 기록 탭이 이미 `FakeRunRecordRepository`를 쓴다.
- **음악 완료를 앱에 알리는 방법이 정해지지 않았다.**

## 4. 사용자가 정한 것

- **진입 두 곳** — 기록카드 탭, 러닝 요약 화면(S15)의 작성 버튼. 요약에서 왔으면
  **그 기록이 기본 선택**이다.
- **기록 고르기는 날짜부터.** 날짜를 고르면 그날 뛴 기록이 목록으로 나온다.
- **러닝 유형 셋** — 일상 · 대회 · 여행. 확정이다.
- **회고글은 필수.** 쓰기 전에는 저장이 안 눌린다.
- **사진은 최대 5장, 선택.** 한 장당 한 화면에서 캡션을 쓰고, 옆으로 밀거나 버튼으로
  다음 장에 간다.
- **공개범위 셋** — Public · Friends · Private. `Friends`가 맞다.
- **음악 생성도 선택이다.** 켜고 끈다.
- **인스타그램 게시글 꼴에 릴스 세로 비율.** 사진은 9:16으로 강제 크롭한다.
- **기록카드 탭은 월 캘린더.** 날짜 칸이 곧 썸네일이고, 썸네일은 첫 번째 사진이다
  (11/09 회의록). 러닝 유형 필터가 붙는다.
- **확대·축소는 단계형, 월 ⇄ 분기 두 단계.** 연은 안 한다.
- **공개한 카드(Public·Friends)가 프로필 인사말 아래 그리드로.**
- **이번엔 Fake로 간다.** 백엔드 질문 문서를 따로 만들어 던져 둔다.

## 5. 접근 — 왜 이렇게 짓나

협의가 필요한 건들과 REST 명세 부재를 어떻게 다룰지가 갈림길이었다.

| | 어떻게 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| ① 전부 Fake로 먼저 | 미정 건을 추측으로 메우고 화면을 다 짓는다 | 안 막힌다 | 계약이 어긋나면 음악 상태와 공개범위를 다시 짓는다 |
| ② 협의 끝나고 시작 | 답을 받고 시작한다 | 재작업이 없다 | 명세가 없어 언제 풀릴지 모른다. 그동안 멈춘다 |
| ③ **겹친다 (채택)** | 질문 문서를 던져 두고, 그 결정에 **안 걸리는 것**부터 짓는다 | 멈추지 않고, 다시 지을 자리가 적다 | 결정이 늦으면 마지막 PR이 밀린다 |

②와 ③의 차이는 재작업량이 아니라 **멈춰 있는 시간**이다. 대기방 채팅도 ③으로 갔고
계약이 바뀐 자리는 적었다.

- **세로로 끝없이 이어진다.** 달 머리가 중간중간 선다. 캘린더를 좌우로 넘기면
  어디까지 왔는지 모른다(기록 탭 캘린더가 같은 이유를 적어 뒀다).
- **요일 머리를 둔다.** 시안에는 없는데, 없으면 칸이 무슨 요일인지 알 수 없다.
- **하루에 카드가 둘 이상일 수 있다.** 하루에 두 번 뛰면 기록이 둘이고, 기록마다
  카드가 하나씩이다. 칸에는 **최신 카드의 썸네일 + 오른쪽 위 작은 개수 배지**를
  둔다. 누르면 **1장이면 바로 상세로, 2장 이상이면 그날 카드 목록 시트**가 뜬다.
- **사진이 없는 카드도 칸을 채운다.** 사진 0장이면 **그날의 경로 선 아트**를 그린다.
  빈 날과 구별돼야 한다 — 썸네일이 없다고 칸을 비우면 카드를 쓴 날이 안 쓴 날처럼
  보인다. 선은 모양이 날마다 달라 유형 아이콘보다 알아보기 쉽다.
- **빈 날을 누르면** 그날 러닝 기록이 있을 때만 그 날짜가 꽂힌 작성으로 간다.
  기록이 없으면 아무 일도 일어나지 않는다.
- **핀치하면 분기 보기.** 같은 7열 그리드인데 칸이 작아져 **세 달이 한 화면에**
  들어온다. **역법 분기**(1–3월, 4–6월 …)로 묶고 머리는 `2026 3분기 · 카드 24장`
  이다. 칸이 작아 날짜 숫자는 뺀다.
- **받은 달은 다시 받지 않는다.** 분기로 펴면 아직 못 받은 달만 채운다. 분기 전환이
  그 자체로 세 번 부르는 것이 아니라, **이미 받은 달은 그대로 쓰고 모자란 것만
  채우는** 것이다.
- **스크롤 범위**: 과거는 첫 카드가 있는 달까지, 미래는 이번 달까지. 끝에 닿으면 세
  달씩 더 받는다.
- **유형 필터는 단일 선택.** 걸면 안 맞는 날은 **썸네일만 빠지고 날짜 칸은 남는다**
  — 칸이 사라지면 달력이 아니게 된다. 달 머리 숫자는 **필터를 적용한 수**다. 탭을
  떠나면 `전체`로 돌아간다.
- **빈 상태**: 카드가 하나도 없어도 캘린더는 그대로 두고, 위에 한 줄 안내와 쓰기
  버튼을 둔다. 캘린더를 치우면 이 탭이 뭘 하는 곳인지 알 수 없다.

### 6-2. 작성 1 — 기록 고르기 · 유형 · 회고

```
┌─────────────────────────────────┐
│ ←      기록카드 쓰기      다음   │
├─────────────────────────────────┤
│ 러닝 불러오기                    │
│ ┌─────────────────────────────┐ │
│ │ 2026.09.02 (화)          📅 │ │
│ └─────────────────────────────┘ │
│ ┌─────────────────────────────┐ │
│ │ ● 18:54  5.4km  28:10       │ │
│ │ ○ 07:12  3.1km  18:40  카드 │ │   `카드` = 이미 있음
│ └─────────────────────────────┘ │
│ ┌─────────────────────────────┐ │
│ │     경로 선 아트 (9:16)       │ │
│ └─────────────────────────────┘ │
│  총 거리   평균 페이스   총 시간  │
│                                 │
│ 러닝 유형                        │
│ [일상] [대회] [여행]             │
│                                 │
│ 러닝 메모                        │
│ ┌─────────────────────────────┐ │
│ │ 오늘의 러닝은 어떤 순간으로   │ │
│ │ 기억되나요?                  │ │
│ └─────────────────────────────┘ │
└─────────────────────────────────┘
```

- **러닝 요약에서 왔으면** 날짜와 기록이 골라져 있다. **그 기록에 이미 카드가 있으면
  곧장 그 카드의 수정 화면으로 보낸다** — 작성 화면을 띄워 놓고 못 쓰게 하는 것보다
  낫다.
- **`카드` 표시를 붙이고, 누르면 수정으로 보낸다.** 회색으로 죽이면 왜 못 고르는지
  알 수 없다. 카드 유무는 **기록 목록 응답이 실어 주는 값**으로 판단한다(10절 질문 3).
- 그날 뛴 기록이 없으면 목록 자리에 한 줄로 알린다.
- **`다음`은 기록 · 유형 · 회고가 다 차야 켜진다.**
- 회고는 1000자까지.

### 6-3. 작성 2 — 사진

```
┌─────────────────────────────────┐
│ ←      사진 (2/5)         다음   │
├─────────────────────────────────┤
│       ┌───────────────┐         │
│       │   9:16 크롭    │         │   밀어서 다음 장
│       └───────────────┘         │
│        ○ ● ○ +                  │   + = 한 장 더
│ ┌─────────────────────────────┐ │
│ │ 이 사진에 한마디 (선택)      │ │
│ └─────────────────────────────┘ │
│       [이 사진 지우기]           │
└─────────────────────────────────┘
```

- **사진은 선택이다.** 한 장도 없이 `다음`을 누를 수 있다.
- **`+`로 한 장씩 고르고, 고르면 바로 크롭 화면이 뜬다.** 여러 장을 한꺼번에 고른 뒤
  크롭을 다섯 번 연달아 하게 만들지 않는다. 9:16 틀은 고정이고 사진을 움직여 맞춘다.
  프로필 커버에 쓴 `ui_image_cropper.dart` · `cover_crop.dart`를 비율만 바꿔 쓴다.
- 한 장 10MB까지. 프로필 사진과 같은 상한이고, 같은 자리에서 검사한다.
- **서버에 올리는 원본은 크롭 결과다.** 원본 그대로 올리면 AI가 보는 그림과 사람이
  본 그림이 달라진다.
- **썸네일도 크롭 결과에서 만든다** — 9:16, 긴 변(세로) 320px. `flutter_image_compress`.
- 캡션은 100자까지. 선택이지만 **AI가 사진 음악을 만들 때 읽는 값**이다 — 그 사실을
  한 줄로 알려 준다.

### 6-4. 작성 3 — 공개범위 · 음악

┌─────────────────────────────────┐
│ ←        저장하기         저장   │
├─────────────────────────────────┤
│ 누가 볼 수 있나요                 │
│  ○ 전체 공개   누구나 봅니다      │
│  ● 친구 공개   친구만 봅니다      │
│  ○ 나만 보기                     │
│                                 │
│ ⚠ 공개하면 달린 경로가 지도로     │
│    함께 보입니다                  │
│ ─────────────────────────────── │
│ AI 음악 만들기            [ON]   │

- **경고 한 줄은 `전체 공개`와 `친구 공개`에서만 뜬다.**
- 음악 토글 기본값은 **켜짐**. 공개범위 기본값은 **친구 공개**.
- `저장`을 누르면 카드가 만들어지고 **상세로 간다**(작성 화면들은 스택에서 걷힌다).

### 6-5. 카드 상세 — 포토북

> **2026-11-16 변경.** 사용자가 상세를 **포토북**으로 바꿨다. 큰 사진 한 장이
> 가운데 서고 양옆 이웃이 살짝 보이며, **그 장의 음악이 끝나면 자동으로 다음
> 장**으로 넘어간다. 진행 표시는 점이 아니라 **장마다 차는 막대**다.
>
> ⚠️ **음악이 아직 없어** 넘기는 조건을 "그 장의 길이만큼 지나면"으로 둔다
> (기본 30초·사진 10초). 음악이 붙으면 **길이의 출처만** 실제 재생 끝 신호로
> 바꾼다 — 화면 구조는 그대로다.
>
> 탭하면 멈추고 다시 탭하면 이어간다. 손으로 밀면 그 장부터 다시 센다.
> **마지막 장에서는 멈춘다** — 처음으로 되돌아가지 않는다.

```
┌─────────────────────────────────┐
│ ←   2026.09.02 · 18:54       ⋮  │   ⋮ = 수정 · 삭제
├─────────────────────────────────┤
│ ┌─────────────────────────────┐ │
│ ┌─┐┌───────────────────────┐┌─┐│   양옆 이웃이 살짝 보인다
│ │ ││   9:16 한 장          ││ ││   1장: 경로 선 아트
│ │ ││                       ││ ││   2~6장: 사진
│ └─┘└───────────────────────┘└─┘│
│          "바닷가에서"            │   사진 장의 캡션
│        ▮▮▮▯▯▯                   │   장마다 차는 막대
│ ♪ 음악 만드는 중…                │
│ 👤👤👤 +1  함께 뛴 러너가 4명     │
│ ─────────────────────────────── │
│  총 거리   평균 페이스   총 시간  │
│  5.4 km    5'38"/km     28:10   │
│ ─────────────────────────────── │
│ [일상]              🔒 나만 보기 │
│ 러닝 메모 …                      │
└─────────────────────────────────┘
```

- **페이저 1장은 경로 선 아트다.** 사진이 없으면 그 한 장뿐이다.
- **`RunMapView`를 쓰지 않는다.** `CustomPainter`로 직접 긋는다 — 지도 제스처가 없어
  페이저와 다투지 않고, `NAVER_MAP_CLIENT_ID`가 없는 빌드에서도 그대로 그려진다.
- **음악 줄은 카드 하나에 하나다.** 곡별 상태가 없다(3절).

  | 상태 | 줄 |
  |---|---|
  | 생성 안 함 | `♪ AI 음악 만들기` (누르면 요청) |
  | `QUEUED` | `♪ 음악 생성 준비 중…` |
  | `PROCESSING` | `♪ 음악 만드는 중…` |
  | `SUCCEEDED` | `▶ 재생` |
  | `FAILED` | `♪ 음악을 만들지 못했어요  [다시 만들기]` — **전곡을 다시 만든다** |

- **보고 있는 장의 곡이 흐르고, 끝나면 다음 장으로 넘어간다.** 경로 장에서는 기본
  30초 곡, 사진 장에서는 그 사진의 10초 곡. **이번 라운드에는 소리가 없고 길이만
  쓴다**(8절).
- **`🔒 나만 보기` 칩을 누르면 공개범위만 바꾸는 시트**가 뜬다. 공개범위는 음악 입력이
  아니라 **재생성을 부르지 않는다** — 그래서 지름길을 둔다.
- 남의 카드면 `⋮`가 없다.

### 6-6. 수정 · 삭제

- **수정은 작성 세 화면을 그대로 다시 쓴다.** 라우트도 셋이다
  (`/record-card/:id/edit`, `.../edit/photos`, `.../edit/publish`).
- **수정에서 러닝 기록은 바꿀 수 없다.** `unique(running_record_id)` 때문에 카드가
  있는 기록으로 옮기면 서버가 거절하고, 바꾸면 지표·경로가 통째로 달라져 다른 카드가
  된다. 기록 선택기 자리에 **고른 기록을 읽기 전용으로** 보여 준다.
- **음악이 있고 입력이 바뀌면** 저장할 때 알린다 — 회고·유형·사진·캡션 중 하나라도
  바뀌면 전곡이 다시 만들어진다. 공개범위만 바꾸면 음악은 그대로다.
- **생성 중에도 고치고 지울 수 있다.** 백엔드가 "생성 중 수정·삭제는 활성 요청을
  무효화한다"고 적었다. 막지 않고 **한 줄로 알린다.**
- **삭제는 확인을 받는다.** 논리 삭제가 없어 되돌릴 수 없다. 그 말을 그대로 쓴다.
  지우면 **왔던 곳으로** 돌아간다(캘린더에서 왔으면 캘린더, 프로필에서 왔으면 프로필).

### 6-7. 프로필 그리드

`profile_page.dart`의 `ProfileStatRow` 아래, "아래 본문이 비어 있다. 빠뜨린 것이
아니다"라고 적힌 그 자리다.

```
│  친구 12    받은 요청 2         │
│ ─────────────────────────────── │
│ ┌────┐┌────┐┌────┐              │   3열 · 9:16 · 최신순
│ │ ▣  ││ ▣  ││ ▣  │              │   처음 6장
│ └────┘└────┘└────┘              │
│ ┌────┐┌────┐┌────┐              │
│ │ ▣  ││ ◆  ││ ▣  │              │
│ └────┘└────┘└────┘              │
│          더 보기                 │
```

- **공개한 카드만 선다** — `PUBLIC`과 `FRIENDS`다. **내 프로필에서도 `PRIVATE`는
  안 보인다.** 사용자가 그렇게 정했고, 나만 보는 카드를 보는 자리는 기록카드 탭이다.
- **`UserProfilePage`에도 같은 위젯을 꽂는다.** 그 화면이 이미 내 프로필과 같은 틀을
  재사용한다.
- **거르는 것은 서버다.** 앱이 거르면 안 보여야 할 카드가 이미 기기에 와 있다는 뜻이
  된다.
- 처음 6장(3열 2줄)만 깔고 `더 보기`로 전체 보기 화면에 간다. 전체 보기는 마지막 PR.
- 사진 없는 카드는 캘린더와 같은 **경로 선 아트**로 그린다.
- 카드가 없으면 그리드 자리를 비워 둔다. 남의 프로필에 "아직 없어요"를 띄울 이유가 없다.

### 왜 `record_card/`를 새로 파나

기록(`record`)은 이미 22개 파일이고 탭도 따로다. **러닝 기록 자체는 `record`의
도메인(`RunRecord`)을 가져다 쓴다** — CLAUDE.md가 금지한 것은 다른 feature의
**화면·위젯** import이고, 도메인은 아니다.

프로필 그리드만 `profile/`에 둔다. 반대로 두면 `profile`이 `record_card`의 화면을
import하게 된다.

### 라우트 — **탭만 셸 안, 나머지는 셸 밖**

| 경로 | 화면 | 위치 |
|---|---|---|
| `/record-card` | 탭 (기존 상수 재사용) | 셸 **안** |
| `/record-card/new` · `/new/photos` · `/new/publish` | 작성 1·2·3 | 셸 **밖** |
| `/record-card/:id` | 상세 | 셸 **밖** |
| `/record-card/:id/edit` · `/edit/photos` · `/edit/publish` | 수정 1·2·3 | 셸 **밖** |

셸 밖에 두는 이유가 셋이다.

1. 작성 세 화면에 **하단 탭 바가 보이지 않는다.**
2. **프로필 그리드나 러닝 요약에서 카드를 열어도 탭이 바뀌지 않는다.** 브랜치 안에
   두면 남의 프로필에서 카드를 열었는데 기록카드 탭으로 전환되고, 뒤로 가기가 내
   캘린더로 떨어진다.
3. **iOS에서 브랜치 자체가 `if (showRecordCardTab)` 조건부다.** 셸 안에 두면 탭을
   되살리기 전까지 상세 라우트가 아예 존재하지 않는다.

`app_routes.dart`에 **정렬 위치에 넣는다.** 맨 끝에 붙이면 머지 충돌이 난다
(`docs/CONTRIBUTING.md`).

### 작성 중인 것의 수명

작성이 세 화면이라 라우트를 넘나든다. `cardDraftProvider` 하나가 들고,
**`keepAlive`를 명시한다** — 안 그러면 사진 화면으로 가는 순간 작성 1 화면의 구독이
끊겨 dispose된다(`docs/implementation-notes.md` §5-1).

| 언제 | 어떻게 |
|---|---|
| 저장 성공 | 비운다 |
| 작성 1에서 뒤로 | 쓴 것이 있으면 **확인을 받고** 버린다 |
| 앱을 죽였다 켬 | **사라진다.** 영속화하지 않는다 |
| draft가 있는데 러닝 요약에서 새로 진입 | 덮어쓰기 전에 **알린다** |
| 수정 모드 | **카드 ID별 family로 따로 둔다.** 작성 중에 남의 카드 수정으로 들어가도 안 섞인다 |

## 8. 가짜 데이터

`FakeRecordCardRepository`가 한다.

- **카드 Fake는 러닝 기록 Fake에 매이지 않는다.** 카드가 지표·좌표 스냅샷을 품기
  때문에(3절) 자기 데이터만으로 선다. **`FakeRunRecordRepository._plan`은 건드리지
  않는다** — 기록 탭의 주간·월 요약 눈검증 값이 같이 바뀐다.
- **두 달치 카드 20장.** 유형 셋이 섞이고 공개범위도 섞인다. **사진 0장인 카드,
  5장인 카드, 하루에 둘인 날**이 각각 있어야 한다 — 없으면 유형 타일·개수 배지·그날
  시트를 한 번도 못 보고 넘어간다.
- 작성 화면이 고르는 **러닝 기록 목록은 기존 `FakeRunRecordRepository`를 그대로** 쓴다
  (오늘 기준 16일 안 8건). 카드 유무는 Fake가 자기 목록으로 판단한다.
- **사진은 번들 에셋을 쓴다.** 네트워크를 타지 않는다.
- **음악 상태를 타이머로 흉내낸다.** 저장하면 `QUEUED` → 3초 뒤 `PROCESSING` →
  10초 뒤 `SUCCEEDED`. **스무 번에 한 번은 `FAILED`로 떨군다.**
- **재생은 소리 없이 흉내만 낸다.** `▶`를 누르면 30초(사진 장은 10초)짜리 **진행바가
  찬다.** 장을 넘기면 진행바가 그 장의 길이로 바뀐다. 소리만 없다. 오디오 패키지는
  `pubspec`에 없고, 새 패키지는 승인을 받는다(CLAUDE.md).
- **실패를 흉내낸다.** 목록·상세 조회가 실제처럼 실패하는 길을 둔다
  (`FakeRunRecordRepository`에 전례가 있다). **에러 화면을 눈으로 확인하는 방법**이
  각 PR의 수용 기준에 들어간다.

## 9. 내가 정한 것 (바꿀 것이 있으면 말해 주면 바꾼다)

| | 정한 것 | 왜 |
|---|---|---|
| 달 머리 숫자 | `카드 18장` — **분수를 쓰지 않는다** | 분모가 무엇이든 안 채운 칸이 결손으로 읽힌다. 반목표와 부딪힌다 |
| 하루에 카드 둘 이상 | 최신 썸네일 + 개수 배지, 누르면 그날 목록 시트 | 하루 두 번 뛰면 정상이다. 하나만 열리면 나머지가 갇힌다 |
| 사진 0장 카드 | **경로 선 아트** | 빈 칸과 구별돼야 하고, 날마다 모양이 달라 아이콘보다 알아보기 쉽다 |
| 라우트 위치 | 탭만 셸 안, 작성·상세·수정은 셸 밖 | 7절 세 가지 이유 |
| 수정에서 러닝 기록 교체 | **못 한다** | 바꾸면 지표·경로가 통째로 달라져 다른 카드가 된다 |
| 경로 | **배경 없는 선 아트로 통일.** 내 카드도 남의 카드도 같다 | 사용자가 정했다. 진짜 지도는 기록 탭 상세(S16)에 이미 있다 |
| draft 영속화 | **안 한다** | 반목표를 "세 화면을 넘나드는 동안"으로 좁혔다 |
| `activity_type` 코드 | `DAILY` · `RACE` · `TRAVEL` | AI 문서가 쓴 예시와 같다 |
| `FRIENDS` 미확정 구간 | 앱 enum은 `friends`, **직렬화만 분리.** 서버가 `FOLLOWERS`를 줘도 `friends`로 읽는다. **모르는 값은 `private`로** | 모르면 안 보여주는 쪽이 안전하다 |
| 회고 길이 | 1000자 | 시안 예시 글이 300자쯤이다 |
| 캡션 길이 | 100자 | 사진 한 장에 한마디다 |
| 비속어 | **채팅과 같이 표시만 마스킹한다.** 입력·저장을 막지 않는다 | 사용자가 채팅에서 "표시 마스킹만"으로 정했다. 규칙을 둘로 두지 않는다 |
| 음악 토글 기본값 | 켜짐 | 온보딩이 약속한 기능이다 |
| 공개범위 기본값 | 친구 공개 | 전체 공개가 기본이면 경로가 모르는 사이에 공개된다 |
| 썸네일 | **앱이 크롭 결과에서 만들어 함께 올린다** (9:16, 세로 320px) | 서버에 이미지 처리 파이프라인이 필요 없다 |
| 사진 고르기 | **한 장씩 고르고 바로 크롭** | 다섯 장을 몰아 고른 뒤 크롭을 다섯 번 하면 중간에 그만두기 어렵다 |
| 사진 상한 | 한 장 10MB | 프로필 사진과 같은 값, 같은 검사 |
| 사진 순서 바꾸기 | 안 넣는다 | 5장이라 지우고 다시 넣는 편이 빠르다 |
| 유형 필터 | 단일 선택, 탭을 떠나면 `전체` | 복수 토글은 "왜 이 날이 안 보이지"를 부른다 |
| 분기 묶음 | **역법 분기** (1–3, 4–6 …) | 보던 달 기준 롤링은 머리 숫자가 스크롤할 때마다 바뀐다 |
| 프로필 그리드 | 처음 6장 + `더 보기` | 카드가 많은 사람에게 그리드가 끝없이 늘어나면 안 된다 |
| 음악 재생 패키지 | 이번엔 안 넣는다 | 새 패키지는 승인을 받는다(CLAUDE.md) |

## 10. 백엔드에 물어볼 것

전문 → `docs/notes/2026-11-16-record-card-backend-questions.md`

1. **카드 응답에 정규화 경로·지표·파티원.** 앱이 러닝 쪽에서 다시 가져오는 길이
   막혀 있다(3절). 조각별로 갈린 `0~1` 좌표, 200~300점으로 단순화.
   **이 답에 도메인·Fake·상세 화면이 전부 걸린다.**
2. **서버 draft를 언제 만드나.** `POST /record-cards` → `complete` 두 단계가 사진
   업로드 때문인지, 작성 1에서 바로 만드는지, 사진 화면에서 만드는지.
3. **사진 업로드 엔드포인트가 목록에 없다.** presigned 발급을 어디서 하나.
4. **음악 엔드포인트가 하나도 없다.** 생성 요청·재요청·상태 조회.
5. **카드 모음의 월 조회.** `GET /users/{userId}/record-cards`가 기간·커서를 받나,
   상한은 몇인가.
6. `visibility` — `친구 공개`를 **어느 테이블로 판정**하나. 값 이름은 `FRIENDS`.
7. **기록 목록 응답에 카드 유무**(`recordCardId` 또는 `hasRecordCard`).
8. `activity_type` 허용값 확정 + DB 컬럼명 `activity`와의 차이.
9. **썸네일 키 컬럼.** 만드는 것은 앱이 한다.
10. **음악 완료를 앱이 어떻게 아나.** FCM / 조회 / 폴링.
11. 여섯 엔드포인트의 스키마·일정 + 러닝 기록 목록 API(19번) 일정.
12. 서명 URL 만료 시간.

## 11. 빌더에게 남긴 것

- **분기 보기의 칸 크기.** 세 달이 한 화면에 들어오는 것이 기준이다(412dp 폭 기준
  26×37 언저리). 기기에서 보고 정한다.
- **핀치 제스처와 세로 스크롤의 충돌.** `GestureDetector`의 스케일과
  `CustomScrollView`가 같은 자리에서 다툰다.
- 월 ⇄ 분기 **전환 애니메이션**. 뚝 끊기면 어느 달을 보고 있었는지 잃는다.
  `AppMotion` 토큰 안에서 고른다.
- **`Semantics`** — 캘린더 칸(날짜 + 카드 유무 + 장수), 사진 페이저(몇 번째 장),
  유형 타일. 탭 바에 글자 라벨이 없는 것과 같은 문제다.
- ⚠️ **선 아트의 가로세로 비.** 위도와 경도를 그대로 x·y에 꽂으면 모양이 틀어진다.
  경도 1도의 실제 거리는 위도 1도의 `cos(위도)`배라, 서울(37.5°)이면 약 **0.79배**다.
  보정 없이 그리면 **동서로 1.26배 늘어난** 경로가 된다. 경도 폭에 `cos(위도)`를
  곱한 뒤 9:16 안에 맞춘다. **서버가 정규화해 주더라도 같은 보정이 필요하다** —
  정규화는 범위를 `0~1`로 바꿀 뿐 종횡비를 고쳐 주지 않는다. 서버가 보정까지 해서
  준다면 앱은 하지 않는다. 어느 쪽인지 확인하고 **한 번만** 한다.
- **선이 한 점으로 뭉치는 경우.** 트레드밀이나 GPS가 거의 안 움직인 러닝은 bounding
  box가 0에 가까워 0으로 나눈다. 최소 크기를 정해 두거나 점 하나를 그린다.
- 라우트 선언 순서 (`/new`가 `:id`에 먹히지 않게).
- `record_card_state`의 sealed union 작성 방식. freezed 미도입이라 `record_state.dart`
  전례를 따른다.
- `AppStrings` 삽입 위치 — **정렬 위치에.** 맨 끝에 붙이면 충돌한다.
- **썸네일 캐시는 `ProfilePhotoImage`를 그대로 쓴다.** 서명을 뗀 경로를 캐시 키로 써서
  서버가 매번 새 서명 URL을 줘도 다시 받지 않는다. ⚠️ **이번 라운드에는 검증되지
  않는다** — Fake가 번들 에셋을 써서 네트워크를 한 번도 타지 않는다. 서버가 붙는
  날 처음 확인된다. 메모리 캐시라 앱을 껐다 켜면 다시 받는다는 것도 그때 드러난다.
- 빈 상태·다크·라이트는 화면마다 전부. CLAUDE.md 규칙이다.
