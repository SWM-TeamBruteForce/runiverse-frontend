# UI 전면 교체 작업 환경 설계

화면 20개의 디자인을 통째로 바꾼다. **기존 기능을 깨뜨리지 않으면서** 그렇게 하기
위한 구조·절차를 정한다.

이 문서는 **디자인 자체가 아니라 디자인을 갈아끼우는 방법**을 다룬다. 어떤 화면이
어떻게 생겼는가는 Figma가 정본이고, 여기서는 그것을 안전하게 들여오는 길만 적는다.

---

## 1. 무엇이 위험한가

지금 앱에는 **화면 20개 · 공용 위젯 11개**가 있고, 그것을 지키는 그물은
**위젯 테스트 262개(24파일)** 하나뿐이다. 골든 테스트는 없다.

문제는 그 테스트들이 **동작과 구조를 함께 단정**한다는 것이다.

```dart
// 동작을 보는 것 같지만 실은 부품 이름에 묶여 있다
final cta = tester.widget<AppButton>(
  find.widgetWithText(AppButton, AppStrings.homeMatchCta),
);
expect(cta.onPressed, isNull);
```

화면 구성이 바뀌면 이런 단정이 무너지고, **동작을 지켜주던 그물이 바로 그 순간
사라진다.** 가장 검증이 필요한 시점에 검증 수단을 잃는 것이 이 작업의 핵심 위험이다.

### 실측

구조에 기댄 단정을 세어 보면 다음과 같다.

| 패턴 | 건수 | 재설계 후 |
|---|---|---|
| `find.byType(화면클래스)` | 69 | **살아남는다** — 라우팅 단정이고 화면 클래스는 그대로다 |
| `find.byType(부품)` | 44 | 위태롭다 — `TextField` 32건이 대부분 |
| `widgetWithText(부품, …)` | 51 | 위태롭다 |
| `tester.widget<부품>(…)` | 21 | 위태롭다 |
| `findsNWidgets` · `.at()` · `descendant` | 28 | 위태롭다 — 개수와 위치에 기댄다 |

**144건이 위태롭고**, `onboarding_flow_test`(38) · `sign_in_page_test`(19) ·
`profile_setup_test`(14) · `match_register_test`(14)에 몰려 있다.

부품 44건의 내역은 `TextField` 32 · `ProfileAvatar` 2 · `ListView` 2 ·
`NavigationBar`·`InkWell`·`HomeHero`·`EmptyStateCard`·`AppButton`·`TextButton`·
`Scrollable`·`CircularProgressIndicator` 각 1이다.

⚠️ **144 는 상한이지 예측이 아니다.** 실제로 몇 개가 깨질지는 새 디자인이
`AppStrings` 와 부품 이름을 얼마나 유지하는가에 달려 있고, 그것은 아직 모른다.
5절이 선투자를 접은 이유가 이것이다.

## 2. 정한 것 넷

| 갈림길 | 정한 것 |
|---|---|
| 교체 범위 | **화면 구성까지 전부** — 레이아웃·흐름·위젯 배치가 바뀐다 |
| 진행 방식 | **화면 하나씩**, 매번 `dev`에 머지 |
| 토큰 시점 | **새 토큰을 따로 두고** 옮긴 화면만 쓴다 |
| 안전망 | **에뮬레이터 확인이 1차 검증.** 깨진 테스트는 그 PR 안에서 고친다 |

화면 하나씩 가는 이유는 **언제든 앱이 동작하고, 깨지면 그 화면만 되돌리면** 되기
때문이다. 긴 브랜치에서 한 번에 바꾸면 그동안 `dev`와 멀어져 마지막 합치기가
위험해진다.

## 3. 병존 구조

```
lib/core/theme/v2/     새 색·타이포·간격·반경
lib/core/widgets/v2/   새 부품 (필요해질 때만 만든다)
```

옮긴 화면은 `v2`만 import하고, 안 옮긴 화면은 기존 것을 그대로 쓴다.

### ⚠️ 한 화면 안에서 두 세대를 섞지 않는다

이것이 이 구조의 **유일한 규칙**이다. 섞이면 "어디까지 옮겼나"를 코드로 답할 수
없고, 되돌릴 때 무엇을 되돌려야 하는지도 흐려진다.

진행 상황은 import 한 줄로 드러난다.

```
grep -rl "theme/v2" lib/features    # 옮긴 화면
```

### ⚠️ 공용 위젯이 결합점이다

`AppButton` 같은 부품은 기존 토큰을 읽는다. 옮긴 화면이 그것을 그대로 쓰면
**반쯤 옛날 모습**이 된다.

그렇다고 `widgets/v2`를 미리 다 만들지는 않는다. **첫 화면을 옮기다 안 맞는 것이
나오면 그때 만든다.** 안 맞는 게 없으면 기존 부품을 그대로 쓴다 — 쓰지도 않을
부품을 두 벌 만드는 것이 더 비싸다.

### 왜 다른 방법을 안 쓰나

| 방법 | 왜 안 쓰나 |
|---|---|
| 옮긴 화면을 새 `Theme`으로 감싼다 | 색은 되지만 **타이포·간격은 정적 상수**라 안 덮인다. 덮으려면 전부 `ThemeExtension`으로 옮기는 리팩터가 얹힌다 |
| 토큰 값을 그냥 덮어쓴다 | **아직 안 옮긴 화면이 즉시 이상해진다.** 점진 교체와 맞지 않는다 |

## 4. 되돌릴 자리

**별도 복제본이나 백업 브랜치를 만들지 않는다.** 화면 하나가 PR 하나이므로
되돌리기는 `revert` 하나다. 복제본을 두면 그쪽이 낡아가면서 오히려 위험해진다 —
되돌릴 곳이 최신이 아니게 된다.

대신 시작점에 태그를 하나 단다.

```
git tag pre-redesign upstream/dev
git push upstream pre-redesign
```

쓰임은 둘이다.

- 전면 철회가 필요할 때 돌아갈 지점
- `git diff pre-redesign..dev -- lib/features/home` 으로 **화면별로 무엇이 바뀌었는지**
  언제든 보는 것

## 5. 안전망

### 1차 검증은 에뮬레이터다

골든 테스트가 없으므로 **그림이 맞는지는 사람이 본다.** 화면마다 다크·라이트 두
테마를 직접 눌러 본다. 이것이 유일한 시각 검증이고, 도입할 계획도 없다 — 교체할
때마다 기준 이미지를 다시 뜨는 비용이 얻는 것보다 크다.

### ⚠️ 테스트를 미리 손보지 않는다

처음에는 1절의 144건을 교체 **전에** 일괄로 구조에서 떼어내려 했다. 접었다.

**어느 단정이 실제로 깨질지 지금은 모르기 때문이다.** 새 디자인을 아직 안 봤고,
`AppStrings` 와 화면 클래스가 유지되면 상당수가 그냥 살아남는다. 살아남을 것까지
미리 손보는 것은 낭비이고, 더 나쁘게는 **멀쩡한 테스트를 건드려 약하게 만든다.**

대신 **실제로 깨진 것만, 새 구조를 보고 나서** 고친다.

### ⚠️ 빨간 것을 다음 PR로 넘기지 않는다

이것이 이 설계의 **유일한 강제 규칙**이다.

> 모든 PR 은 `analyze 0` + **스위트 전체 통과** 상태로 머지한다.

깨진 테스트는 그 PR 안에서 고친다. 총 작업량은 미리 하나 그때 하나 같지만, 그때
하면 **실제로 깨진 것만** 고치게 된다.

넘기면 안 되는 이유는 **빨간 스위트가 읽히지 않기 때문**이다. 화면 셋을 옮겨 60개가
빨개지면 "예상된 빨강" 과 "진짜 고장" 을 구분할 사람이 없어진다. 그 순간 909개
그물 **전체가 같이 침묵한다** — 웹소켓·트랙 순번·세션 만료처럼 재설계가 건드리지도
않는 곳까지 보호가 사라진다.

### 고칠 때 참고표

*할 일 목록이 아니라*, 깨진 단정을 만났을 때 어느 쪽으로 옮길지 정하는 기준이다.

| 깨진 것 | 옮길 곳 | 왜 |
|---|---|---|
| `find.widgetWithText(AppButton, '시작')` | `find.text('시작')` | 부품이 바뀌어도 산다 |
| `tester.widget<AppButton>(…).onPressed` 가 `null` 인가 | **탭해 보고 아무 일도 안 일어나는지** | 잠김을 부품이 아니라 동작으로 본다 |
| `find.byType(TextField)` 로 n 번째 입력 | 라벨·힌트 문구로 찾는다 | 입력 부품이 바뀌어도 산다 |
| `findsNWidgets(3)` | 각 항목이 있는지 | 개수는 배치가 정한다 |

**화면 클래스 단정 69건은 건드리지 않는다.** 라우팅을 보는 것이고 화면 클래스는
이름이 유지된다.

### 판정 기준

고친 뒤에도 **테스트가 실패할 수 있어야 한다.** 단정을 느슨하게 해서 통과만 시키면
그물이 아니라 장식이 된다. 고칠 때마다 "이 화면의 동작이 망가지면 이게 빨개지는가"를
묻는다.

### 먼저 해 본 한 화면

`profile_edit_page_test` 로 전환 방식을 확인했다(2026-09-25).

- 구조 결합 11건 중 **4건은 화면 클래스라 손댈 필요가 없었고**, 7건만 옮겼다
- 저장 버튼 2건은 `tester.widget<TextButton>(…).onPressed` 에서 **눌러 보고
  서버로 나갔는지**로 옮겼다
- 소개글 입력 5건은 `find.byType(TextField)` 에서 **키**(`ValueKey('profile-introduction')`)로
  옮겼다. 입력은 문구로 찾기 어렵다 — 힌트는 비었을 때만 보인다

⚠️ **키는 계약이다.** 그 화면을 새 디자인으로 옮길 때 키를 이어받지 않으면
테스트가 깨진다. 화면 교체 PR 마다 확인한다.

전환 뒤 잠금 조건을 일부러 부수어 테스트가 빨개지는 것을 확인했다. 느슨해져
통과만 하는 상태가 아니다.

## 6. 화면 하나당 흐름

```
브랜치 → 화면 교체 → analyze 0 → 테스트 전체 통과 → 에뮬레이터 확인 → PR → 머지
```

- **PR 하나 = 화면 하나.** 그 화면 때문에 새로 만든 `widgets/v2` 부품도 같은 PR에 넣는다
- 테스트가 깨지면 **5절 참고표로 옮겨 본다.** 그래도 안 되면 그 단정은 정말 구조를
  보고 있던 것이니 새 구조에 맞게 다시 쓴다. **어느 쪽이든 그 PR 안에서 끝낸다**
- 에뮬레이터 확인은 **다크·라이트 두 테마** (CLAUDE.md 규칙)
- 커밋·PR 규칙은 `docs/CONTRIBUTING.md` 를 따른다. base 는 `dev`

### 첫 화면은 파일럿이다

절차 자체를 검증하는 것이 목적이다. **위험이 낮고 다른 화면과 얽히지 않은 것**으로
고른다 — `settings_page` 나 `onboarding_intro_page` 같은.

⚠️ 다만 `settings_page_test` 는 구조에 기댄 단정이 **1건**뿐이라, 아래 2번을 재는
자리로는 값이 거의 없다(2026-09-25 실측). 고를 때 같이 본다.

거기서 확인할 것 셋:

1. `theme/v2` 구조가 실제로 쓸 만한가
2. **테스트가 몇 개나 깨지는가** — 5절이 선투자를 접었으므로 여기가 그것을 재는 자리다
3. 한 화면이 PR 하나로 떨어지는가 (공용 부품이 딸려 나와 커지지 않는가)

**파일럿에서 어긋나면 이 문서를 고친다.** 나머지 19개를 같은 방식으로 밀어붙이기
전에 바로잡는 것이 목적이다.

한 화면에 20개씩 깨지면 5절의 판단을 다시 본다 — 그때는 남은 화면에 대해 일괄
선작업이 값을 할 수도 있다.

## 7. 마무리

마지막 화면을 옮기면:

1. 기존 `theme/`·`widgets/` 의 옛 파일을 지운다
2. `v2/` 를 본래 자리로 올리고 import 를 일괄 정리한다
3. `pre-redesign` 태그는 남긴다

이 정리도 **PR 하나**로 낸다. 그 PR 은 파일 수가 많지만 내용은 이동·이름 변경뿐이라
사유를 본문에 적는다.

---

## 8. 아직 안 정한 것

- **화면 순서** — 파일럿 다음의 순서는 Figma 를 보고 정한다. 서로 부품을 많이
  공유하는 화면끼리 묶으면 `widgets/v2` 를 두 번 만들지 않아도 된다.
- **Figma 파일** — 작업 시작할 때 링크를 받는다. 화면별 대응표를 그때 이 문서에 붙인다.
