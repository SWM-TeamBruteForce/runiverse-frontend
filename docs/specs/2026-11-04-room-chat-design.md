# 대기방 채팅 설계

- 날짜: 2026-11-04
- 상태: **백엔드 협의 전.** 화면과 가짜 구현만 먼저 만든다
- 범위: 매칭 러닝 방 · 초대 러닝 방의 **출발 전 대기 화면**

---

## 1. 무엇을, 왜

출발 시각까지 사람들은 각자 다른 장소에서 기다린다. 지금 그 시간에 할 수 있는 것이
없다 — 명단과 남은 시간만 본다. 같이 뛸 사람에게 한마디 건넬 자리를 만든다.

기대하는 대화는 **간단한 인사말과 정보 공유**다. "곧 도착해요", "조금 늦어요",
"오늘 비 와요" 수준. 길게 떠드는 공간이 아니다.

백엔드와 협의가 안 됐다. 그래서 이번에 만드는 것은 **화면과 가짜 데이터**이고,
`ChatRepository` 경계까지 그려 둔 뒤 **가짜 구현만 끼워 둔다.** 서버가 생기면
가짜를 진짜로 바꾸는 것이 전부가 되도록 한다.

## 2. 목표 · 비목표 · 반목표

### 목표

- 대기 화면에서 채팅을 열고 메시지를 주고받는 **화면이 완성돼 있다.** 다크·라이트
  둘 다, loading·data·error 3분기, empty 상태까지
- 안 읽은 메시지가 있다는 것을 **대기 화면에서** 알 수 있다
- 서버가 생겼을 때 **갈아 끼울 경계**가 있다 — 화면은 `ChatRepository`만 알고,
  그 구현이 가짜인지 진짜인지 모른다
- 백엔드에 들고 갈 **질문 목록**이 이 문서에 남는다 (9절)

### 비목표 (지금 안 만든다, 나중에 할 수 있다)

- **러닝 중 채팅.** 뛰는 동안은 화면을 볼 수 없다
- **읽음 확인 — 누가 읽었는지.** 내가 안 읽은 메시지가 몇 개인지는 범위 **안**이다
  (배지). 남이 내 메시지를 읽었는지는 범위 밖이다
- **전송 실패·재시도 UI.** 서버가 없으면 실패 조건을 정할 수 없다. 낙관적 버블을
  서버 응답으로 되맞추는 문제(9절 #8·#10)와 한 묶음이라, 협의 뒤에 함께 설계한다.
  지금은 보낸 것이 바로 보이고 실패하지 않는다
- **글자 수 제한.** 서버 한도를 모른다 (9절 #5). 조용히 잘리는 것이 가장 나쁘므로,
  한도를 정하기 전에는 아예 두지 않는다
- 사진·파일 첨부, 이모지 반응, 답장 인용
- 메시지 삭제·수정, 신고·차단
- 푸시 알림
- 방 밖(홈·알림)에서 채팅으로 바로 들어가기
- 영속화. 앱을 끄면 가짜 메시지는 사라진다

### 반목표 (이것이 되면 실패다)

- **GPS 좌표·경로가 채팅을 타고 새는 것.** "여기 있어요" 같은 위치 공유 칩, 지도
  링크, 좌표 문자열 전부 금지다. 파티원에게 위치를 드러내지 않는 것이 제품 정책이고
  채팅은 그 정책의 **구멍이 되기 가장 쉬운 자리**다
- 순위·경쟁 프레임의 문구. 빠른 답장 칩에 "내가 1등" 같은 말을 넣지 않는다
- "친구"라는 단어
- **가짜가 진짜 계약처럼 굳는 것.** 서버 모양을 모르는 채로 정한 필드가 나중에
  백엔드를 끌고 가면 안 된다. 코드와 이 문서에 가짜임을 명시한다

## 3. 제약

프로젝트 규칙(`CLAUDE.md` · `docs/implementation-notes.md`)에서 이 작업에 직접
걸리는 것만 옮긴다.

- 색·치수·타이포·문자열은 전부 토큰. `core/theme/tokens/` 밖에서 `Color(0x...)` 금지
- **이모지는 제품 UI에 쓰지 않는다** (`implementation-notes.md` 7-2). 빠른 답장
  칩도 제품 UI다
- **색이 유일한 전달 수단이면 안 된다** (같은 절). 닉네임 색은 글자에 얹는 것이고
  이름 자체가 정보를 들고 있으므로 이 규칙을 지킨다
- UI 텍스트는 한국어
- `StateProvider`/`StateNotifierProvider` 금지 (Riverpod 3)
- freezed 미도입 → 상태는 손으로 쓴 sealed class. 프로젝트가 이미 그렇게 한다
- WebSocket 미도입. **새 패키지를 넣지 않는다** — 가짜 구현은 `dart:async`로 충분하다
- `presentation → domain ← data`. presentation은 data를 import하지 않는다
- **provider끼리 서로 듣지 않는다.** Riverpod이 `CircularDependencyError`로 막는다.
  이것이 6절의 모양을 결정한다
- **Stream 구독은 `ref.onDispose`에서 취소한다** (`implementation-notes.md` 9-2)
- 아이콘: 이 화면은 **v2로 옮긴 화면**이다. `AppIcon`만 쓰고 Lucide와 섞지 않는다
  (`core/widgets/v2/app_icon.dart`). 쓸 아이콘은 5-3절에서 정했다 — **Lucide를
  들이지 않는다**
- 한 PR 20파일 / 500줄

## 4. 사용자가 정한 것

브레인스토밍에서 나온 결정이다. 바꾸려면 다시 물어야 한다.

1. **출발 전 대기방만.** 러닝 중은 아니다
2. **원형 버튼을 우측 하단에 둔다.** 누르면 **별도 채팅 페이지**가 열린다.
   배치는 `나가기` 버튼 **바로 위** — 겹치지 않는다. 겹치는 안(A안)은 목업에서
   보고 버렸다
3. 안 읽은 메시지 **개수 배지**를 버튼에 붙인다
4. 채팅 페이지에 **빠른 답장 칩**을 둔다. 입력창 위, 평범한 채팅창만 두지 않는다
5. 채팅 제목은 `출발시간 - 목표거리 러닝 000님외 n명`으로 표준화하고,
   **두 줄로 나눈다**
6. **가짜 구현만 끼워 둔다.** 경계는 지금 그린다

## 5. 화면

### 5-1. 대기 화면의 채팅 버튼

`match_room_page.dart`에 붙는다.

**왜 `Scaffold.floatingActionButton`이 아닌가.** 이 화면은
`Scaffold(body: SafeArea(Column([Expanded(ListView), Padding(나가기 버튼)])))`이고
`나가기`가 **`body` 안에** 있다(`match_room_page.dart:114-186`). Scaffold의 FAB은
body 위에 떠서 `나가기`를 가린다 — 사용자가 버린 A안이 그렇게 된다.
`Expanded(ListView)`를 `Stack`으로 감싸고 그 안에 띄운다. 그러면 버튼이 목록 위에
뜨고 `나가기` **위에서** 멈춘다.

- 모양: 원형, `primary` 배경. 그 위에 말풍선 아이콘을 **흰색으로 칠해** 얹는다
  (5-3절)
- 배지: 버튼 오른쪽 위. 숫자. **0이면 배지를 그리지 않는다**
- `Semantics(label: ...)` 필수 — 글자 라벨이 없다. 안 읽은 수까지 읽어 준다
- **언제 보이나:** 방이 출발 전(`matching` 또는 `matched`)이고 `!room.isAlone`
  (`room_info.dart:173`)일 때. `started`·`finished`·`cancelled`에서는 숨는다
- 답을 기다리는 초대(`room.invitations`)는 **파티원으로 세지 않는다.** 수락 전에는
  채팅에 들어올 수 없고, 버튼을 켜는 조건에도 넣지 않는다 — 명단에서도 이미 흐린
  별도 묶음이다(`match_room_page.dart:537-544`)

### 5-2. 채팅 페이지

새 라우트. `AppRoutes.matchRoom` 아래 자식으로 둔다.

> ### ⚠️ 우리 코드와 어긋나는 자리 — 여기가 이번 작업의 가장 큰 함정이다
>
> "방을 떠나면 자식도 닫힌다"는 **go_router에서 참이 아니다.** 채팅 페이지를
> 위에 올려 둔 동안 `MatchRoomPage`는 **그대로 살아 있고**, 그 안의 자동 이동
> 두 개가 계속 돈다. 둘 다 **맨 위 라우트**를 건드리므로, 채팅을 열어 둔 사이에
> 엉뚱한 화면을 집는다.
>
> 1. `match_room_page.dart:86-93` — `room == null`이면 `_leaveScreen()`을 부르고,
>    그 안은 `context.pop()`이다(`:361-370`). 채팅이 위에 있으면 **채팅만 닫히고
>    죽은 방 화면에 사람이 남는다** — `:356-360`의 주석이 막으려던 바로 그 상황이다
> 2. `match_room_page.dart:209-222` — `_enterIfDue()`의 `Timer`는 자식을 띄울 때
>    멈추지 않는다. 출발 30초 전이 되면 `pushReplacement(matchCountdown)`을 부르고,
>    이것이 **방 화면이 아니라 채팅 페이지를 갈아치운다**
>
> **그러므로 규칙은 이렇다: 방이 사라지거나 출발 시각이 닥치면 채팅 페이지를
> 먼저 닫고, 그 다음에 기존 이동이 일어난다.** 방법은 빌더가 고른다(두 자리에
> 라우트 확인을 걸든, 자식을 먼저 pop하든). 어느 쪽이든 **채팅을 열어 둔 채
> 출발 시각을 넘기는 경로를 테스트로 덮는다.**

**헤더 — 두 줄.**

```
  19:30 - 5 km 러닝     ← 윗줄, 강조
  영희님 외 2명          ← 아랫줄, textSecondary, 작게
```

한 줄로 붙이면 닉네임이 길 때 `외 n명`이 잘려 나간다 — 몇 명이 있는지가 제목에서
가장 중요한 정보인데 그것이 먼저 사라진다. 그래서 두 줄이다.

조립 규칙:

| 상황 | 윗줄 | 아랫줄 |
|---|---|---|
| 기본 | `19:30 - 5 km 러닝` | `영희님 외 2명` |
| 목표 거리를 모를 때(`targetDistanceMeters == null`) | `19:30 러닝` | 같음 |
| 둘뿐일 때 | 같음 | `영희님과 함께` |

- 시각은 `scheduledStartAt`을 **`AppStrings.matchSlotTime`으로** 적는다. 그 함수가
  한국 시각으로 고정해서 그리는 데는 이유가 있다 — 기기 시간대로 옮기면 있지도
  않은 슬롯 시각이 뜬다(`app_strings.dart:723-727`)
- 거리는 `AppStrings.distanceKm(meters)`를 쓴다. **출력에 공백이 있다**(`5 km`,
  `21.098 km`). 3·5·10km 밖의 값도 그려야 해서 이 함수가 필요하다 — 초대 방에서
  7km가 온다
- **대표 1명**은 `room.players`에서 나를 뺀 **첫 사람**이다. 서버 명단 순서를 쓴다
- `외 n명`의 `n`은 나와 대표를 뺀 나머지 수다
- 뒤로가기로 방으로 돌아간다

**본문 — 메시지 목록.** 아래가 최신. 열면 맨 아래로 간다.

| 종류 | 모양 |
|---|---|
| 내 메시지 | 오른쪽 정렬, `primary` 배경, 흰 글자. 닉네임·사진 없음 |
| 남의 메시지 | 왼쪽 정렬, 프로필 사진 + 닉네임 + 중립 배경 버블. **닉네임 색은 파티 색** |
| 입장 알림 | 가운데, 회색 알약. "영희님이 들어왔어요" |

- **보내는 사람의 이름과 사진은 메시지가 들고 있지 않다.** 화면이
  `message.senderUserId`를 `room.players`에서 찾아 쓴다 — 제목을 그리느라 이미
  읽는 명단이다. 덕분에 탈퇴한 사람이 `탈퇴한 사용자`로 나오는 처리를
  명단과 **한 벌로** 쓴다(`AppStrings.matchRoomDeletedPlayer`,
  `match_room_page.dart:527-535`). 명단에 없는 `senderUserId`도 같은 문구로 떨어진다
  — 나간 사람의 메시지가 남는지는 서버가 정한다(9절 #6)
- 입장 알림의 문구도 **화면이 만든다.** 메시지는 "누가 들어왔다"는 종류와 그
  `senderUserId`만 들고 있다. 그래서 가짜 구현이 닉네임을 알 필요가 없다
- 파티 색은 `partyColorSlot(userId:, myUserId:, order:)`를 쓴다. `order`는
  `room.players`의 서버 순서, `myUserId`는 `authControllerProvider`의
  `AuthSignedIn.userId`. **나는 늘 파랑(0번)** 이다. 러닝 중·결과·카운트다운
  화면과 같은 규칙이라, 채팅에서 본 색이 러닝 중에도 그 사람 색이다
- ⚠️ 파티 색은 **어두운 러닝 화면을 기준으로 고른 레인 색**이다. 라이트 테마의
  `bgBase` 위에서 대비가 아슬아슬한 색이 있다. 닉네임에는 더 짙은 단계가 필요할 수
  있다 — 빌더가 두 테마에서 보고 고른다
- 입장 알림은 **버블과 확실히 달라 보여야 한다.** 회색 알약이 버블처럼 보이면
  누가 한 말인지 모를 발언이 된다
- 시각(`19:28`)은 **버블마다** 붙인다. 같은 사람 연속 메시지를 묶는 규칙은 두지
  않는다 — 가짜 데이터로는 그 규칙이 나은지 검증할 수 없다. 이 시각도 **한국 시각으로
  고정한다**(새 `AppStrings` 항목). 위와 같은 이유다
- empty: "아직 대화가 없어요. 먼저 인사해 보세요." 이때도 칩과 입력창은 보인다
- loading: 목록 자리에 인디케이터. error: 다시 시도 버튼이 있는 안내

**빠른 답장 칩.** 입력창 바로 위, 수평 스크롤.

- 문구(초안, **디자인 확인 필요**): `곧 도착해요` · `조금 늦어요` ·
  `출발 준비 됐어요` · `화이팅!` · `잠시만요`
- **이모지를 넣지 않는다** (3절)
- **탭하면 바로 전송한다.** 입력창을 채우고 한 번 더 누르게 하면 칩을 둔 이유가
  없어진다
- 전송이 끝날 때까지 칩을 잠근다. 안 잠그면 같은 말이 다섯 번 도배된다
- 위치 관련 문구는 넣지 않는다 (2절 반목표)

**입력창.** 1~3줄까지 늘어나는 텍스트 필드 + 전송 버튼. 공백만 있으면 전송 비활성.
보낸 뒤 비우고 포커스를 유지한다. 글자 수 제한은 두지 않는다 (2절).
전송 버튼은 **아이콘 PNG가 버튼 면 자체다** — 따로 원을 깔지 않는다 (5-3절).

### 5-3. 아이콘 — 정해졌다

`AppIcons.all`의 36개에 채팅·메시지·전송에 해당하는 것이 하나도 없다. 그래서
**사용자가 PNG 두 개를 골라 줬다.** Lucide는 들이지 않는다 —
`app_icon.dart:107-110`이 "옮긴 화면은 `AppIcon`만, 섞으면 선 굵기와 모서리가
달라 눈에 띈다"고 못박고, 이 화면은 옮긴 화면이다.

| 쓰는 곳 | 원본 | 모양 |
|---|---|---|
| 대기 화면 채팅 버튼 | `free-icon-chat-bubble-12309678.png` | 말줄임표가 든 말풍선. **단색 검정 선화, 배경 투명** |
| 채팅 페이지 전송 버튼 | `free-icon-up-arrow-6941680.png` | **코랄 원 + 흰 위쪽 화살표.** 두 가지 색이다 |

⚠️ **둘 다 PNG라 `AppIcon` 경로를 못 탄다.** `AppIcon`은 `assets/icons/<name>.svg`만
읽고 색을 덮어쓴다. 이 둘은 `Image.asset`으로 직접 그린다. 아이콘 테스트
(`test/v2_app_icon_test.dart`)는 `.svg`만 추려 대조하므로 PNG를 같은 폴더에 둬도
깨지지 않는다 — 다만 라스터이므로 `assets/images/`에 두는 편이 정직하다.

**색을 어떻게 다루는가, 그리고 왜.**

- **말풍선은 단색이라 틴트가 먹는다.** `primary` 원 위에 흰색으로 칠해 얹는다.
  `AppIcon`이 SVG에 하는 일과 같은 결과다
- **전송 아이콘은 틴트를 걸 수 없다.** 단색으로 칠하면 흰 화살표까지 같이 칠해져
  **화살표가 사라진다.** 그래서 **PNG를 버튼 면 통째로** 쓴다 — 전송 버튼이
  코랄 원이 된다. 파란 원 위에 코랄 원을 또 얹지 않는다
- ⚠️ **이 코랄은 토큰 팔레트 밖의 색이다.** 전송 버튼만 브랜드 파랑에서 벗어난다.
  파랑으로 맞추려면 흰 화살표만 떼어내야 하는데 라스터라 손실이 생긴다 —
  필요하면 화살표를 SVG로 다시 받는다

⚠️ **라이선스.** 파일명이 Flaticon 계열이고, 그쪽 무료 등급은 대개 **출처 표기**를
요구한다. 스토어에 올리는 앱이므로 표기 자리(설정의 라이선스 화면 등)가 필요한지
확인이 필요하다. 코드 작업과 별개로 남는 숙제다.

## 6. 구조

```
lib/features/chat/
  domain/
    chat_message.dart      ChatMessage · ChatMessageKind{text, joined}
    chat_repository.dart   ChatRepository · ChatRoomSeed. 순수 Dart
  data/
    fake_chat_repository.dart   가짜. 이번에 만드는 유일한 구현
  presentation/
    chat_page.dart
    chat_provider.dart
    (버블·칩·헤더 위젯)
```

**새 feature 폴더다.** 매칭 방과 초대 방이 같이 쓰고, 나중에 다른 방에도 붙을 수
있다. `matching` 안에 넣으면 초대 방이 매칭 feature의 화면을 import하는 모양이
된다. `CLAUDE.md`의 feature 목록에 `chat`을 더하는 것은 **수정안만 제안한다** —
요청 없이 그 파일을 고치지 않는다.

`features/session/domain/party_color.dart`를 import하는 것은 규칙에 맞다 —
domain끼리는 feature를 넘어도 된다. 이미 그런 자리가 있다
(`match_countdown_page.dart:492`).

**메시지.**

```dart
enum ChatMessageKind { text, joined }

class ChatMessage {
  final String messageId;
  final String senderUserId;
  final ChatMessageKind kind;
  final String? text;      // kind == text일 때만
  final DateTime sentAt;
  final bool isRead;       // 내가 읽었는가
}
```

`isRead`는 **내가 안 읽은 수를 세기 위한 것**이고, 남이 내 메시지를 읽었는지와는
무관하다(2절). 앱에 이미 같은 모양이 있다 — `AppNotification.isRead`. 서버가 안 읽은
수를 직접 주는지는 9절 #4에서 묻는다.

**경계.**

```dart
abstract interface class ChatRepository {
  Future<List<ChatMessage>> history(ChatRoomSeed seed);
  Stream<ChatMessage> incoming(ChatRoomSeed seed);
  Future<void> send(ChatRoomSeed seed, String text);
}
```

과거 메시지(`history`)와 들어오는 메시지(`incoming`)를 나눈 이유는 **서버가 어느
길로 올지 모르기 때문**이다. WebSocket이든 SSE든 폴링이든 `incoming`이 Stream이면
화면이 바뀌지 않는다.

**`ChatRoomSeed`는 방 번호와 파티원 `userId` 목록을 들고 있다**(`chat_repository.dart`
에 둔다). 파티원 목록은 가짜가 그럴듯한 발신자를 만드는 데 쓴다. 진짜 구현은
그것을 **무시해도 된다** — 이 필드가 서버 계약을 끌고 가지 않는다는 것을 코드
주석에 남긴다.

**provider.** `chatProvider`는 `Notifier`다.

> ⚠️ **`chatProvider`는 `matchRoomProvider`를 듣지 않는다.** provider끼리 서로
> 들으면 Riverpod이 `CircularDependencyError`로 막는다. 그래서 방 번호와 파티원
> 명단은 **화면이** 읽어서 `connect(seed)`로 넣어 준다. 제목과 발신자 이름에 쓰는
> 방 정보도 화면이 `matchRoomProvider`에서 직접 읽는다 — 두 provider를 화면에서 합친다.

- `connect(seed)`를 부르는 것은 **대기 화면**이다. 채팅 페이지를 열기 전부터
  배지에 숫자가 떠야 하므로, 방 화면이 들어올 때 붙는다
- **방 번호가 바뀌면 상태를 비운다.** 안 비우면 전에 있던 방의 메시지가 다음 방에
  보인다
- `keepAlive`를 걸지 않는다. 채팅은 방에 묶인 것이고 방을 떠나면 버린다
- `incoming` 구독은 **`ref.onDispose`에서 취소한다** (3절)
- 채팅 페이지는 열릴 때 "읽었다", 닫힐 때 "닫혔다"를 provider에 알린다. 페이지가
  떠 있는 동안 들어온 메시지는 안 읽은 것으로 세지 않는다

## 7. 가짜 데이터

`FakeChatRepository`:

- `history`는 **열 개 안쪽**으로 준다 — 입장 알림 하나, 상대 몇 개, 내 것 두어 개.
  시각은 `DateTime.now()`에서 몇 분 전으로 흩어 놓는다
- 발신자는 `seed.partyUserIds`에서 돌려쓴다. 그래야 파티 색과 닉네임이 실제 명단과
  맞는다 (이름은 화면이 명단에서 찾는다 — 5-2절)
- **뒤쪽 두 개를 `isRead: false`로 둔다.** 그래야 배지에 숫자가 처음부터 보인다
- `send`는 즉시 목록에 넣고 `incoming`으로 흘린다. **자동 답장은 없다** —
  요청하지 않은 연출이고, 가짜가 살아 있는 것처럼 보이면 서버가 없다는 사실을
  잊게 된다
- **실패하도록 만들 수 있어야 한다.** 늘 성공하면 화면의 error 3분기가 한 번도
  그려지지 않고, 그것을 덮는 테스트도 쓸 수 없다. 생성자에 실패 플래그를 둔다 —
  테스트와 수동 확인용이고, 제품 경로에서는 끄고 쓴다
- 메시지 내용은 2절의 반목표를 지킨다. 좌표·순위·"친구" 없음

| 정한 것 | 왜 |
|---|---|
| 둘뿐일 때 `영희님과 함께` | `외 1명`은 나를 가리키는 말이라 읽기 이상하다 |
| 대표가 탈퇴한 사람이면 건너뛰고 다음 사람 | 탈퇴한 사람을 방의 대표로 내세우는 쪽이 더 나쁘다. 전원 탈퇴면 첫 사람을 그대로 쓴다 |
| 거리를 모르면 윗줄에서 거리만 뺀다 | `19:30 - 러닝`처럼 하이픈이 떠 있는 것보다 낫다 |
| 파티원이 나뿐이면 채팅 버튼을 숨긴다 | 혼자 쓰는 채팅방은 보여줄 것이 없다. 사람이 들어오면 나타난다 — 초대 현황도 그렇게 사라진다 |
| 답을 기다리는 초대는 파티원으로 세지 않는다 | 수락 전에는 방에 들어온 것이 아니다. 명단도 이미 별도 묶음으로 흐리게 그린다 |
| 방이 죽거나 출발 시각이 닥치면 **채팅을 먼저 닫는다** | 안 닫으면 기존 자동 이동이 채팅 라우트를 집어 죽은 방에 사람을 남긴다 (5-2절) |
| 발신자 이름·사진을 메시지에 넣지 않고 **명단에서 찾는다** | 서버 계약을 덜 가정한다. 탈퇴 표기도 명단과 한 벌로 쓴다 |
| 입장 알림 문구를 **화면이** 만든다 | 가짜가 닉네임을 알 필요가 없어진다 |
| 안 읽음을 `ChatMessage.isRead`로 둔다 | 앱에 이미 같은 모양이 있다(`AppNotification.isRead`). 읽음 확인(남이 읽었는지)과는 다른 것이다 |
| 전송 실패 UI는 비목표 | 서버가 없으면 실패 조건을 정할 수 없다. 낙관적 버블 되맞춤과 한 묶음이다 |
| 글자 수 제한을 두지 않는다 | 서버 한도를 모른다. 조용히 잘리는 것이 가장 나쁘다 |
| 시각은 둘 다 한국 시각 고정 | 기기 시간대로 그리면 없는 슬롯 시각이 뜬다 — 이미 밟은 함정이다 |
| 칩을 전송 중에 잠근다 | 안 잠그면 같은 말이 도배된다 |
| `Stack`에 띄운다 (Scaffold FAB 아님) | `나가기`가 `body` 안에 있어서 FAB이 겹친다 (5-1절) |
| 시각을 버블마다 붙인다 | 묶음 규칙이 나은지는 가짜 데이터로 알 수 없다 |
| 칩은 바로 전송한다 | 한 번 더 누르게 하면 칩의 이유가 없다 |
| 새 feature 폴더 `chat/` | 두 방이 같이 쓴다. `matching` 안에 두면 feature를 넘는 import가 된다 |
| 자동 답장 없음 | 요청하지 않은 연출 |
| 가짜에 실패 플래그를 둔다 | 안 그러면 error 3분기가 죽은 코드가 된다 |
| 전송 버튼은 PNG를 **버튼 면 통째로** 쓴다 | 두 색 아이콘이라 틴트하면 화살표가 사라진다. 파란 원 위에 코랄 원을 또 얹을 수도 없다 |
| 두 아이콘을 `Image.asset`으로 그린다 | PNG는 `AppIcon`의 SVG 경로를 못 탄다. Lucide를 들이는 것보다 낫다 |

## 9. 백엔드에 물어볼 것

이 문서를 들고 협의할 때 쓴다. 답이 오면 가짜를 진짜로 바꾸는 작업이 생긴다.

1. **전송 경로.** WebSocket인가, 기존 SSE(`/match-rooms/stream`)에 메시지 이벤트를
   더하고 전송만 POST인가. 앱에는 WebSocket이 아직 없다 — SSE+POST면 패키지를
   더 넣지 않아도 된다
2. **과거 메시지 API.** 경로·정렬·페이지네이션(커서인가 오프셋인가)
3. **보존 기간.** 방이 끝나면 지우는가. 러닝 기록 화면에서 다시 볼 수 있는가
4. **안 읽은 수를 서버가 주는가.** 아니면 앱이 마지막으로 본 메시지 id로 세는가
5. **길이 제한·금지어·신고.** 한 메시지 최대 글자, 도배 제한
6. **탈퇴하거나 나간 사람의 메시지.** 남는가 지워지는가, 닉네임은 익명 처리인가
   (알림·방 명단은 서버가 익명 처리해서 준다)
7. **입장·퇴장 알림을 서버가 만드는가.** 서버 이벤트로 받는가, 앱이 명단 변화를
   보고 만드는가
8. **메시지 id와 순서 보장.** 보낸 것을 즉시 그린 뒤 서버 응답으로 바꿀 때 중복을
   없앨 수단(`clientMessageId` 같은 것)이 있는가
9. **채팅이 열리는 구간.** 서버도 출발 전만 허용하는가. 러닝 중 전송은 거절되는가
10. **전송 실패의 의미.** 어떤 경우에 실패하고, 재시도가 안전한가(중복이 생기는가).
    #8과 함께 답을 받아야 낙관적 버블을 되맞출 수 있다

## 10. 빌더에게 남긴 것

- 버블·칩·배지의 정확한 치수와 색 토큰 선택, 그리고 버튼이 `나가기` 위에서 멈추게
  하는 여백. `나가기`에도 자기 여백이 있어서(`match_room_page.dart:172-178`)
  값을 그냥 베끼면 어긋난다. 기존 화면(`_PartyCard`, `AppButtonV2`, `AppInputV2`)의
  토큰을 따른다
- 빠른 답장 칩 문구 확정 — 5-2절의 다섯 개는 초안이다. **디자인 확인이 필요하다**
- 라우트 이름과 go_router 자식 등록 방식. `AppRoutes.matchRoom`은 셸 밖의 자식
  없는 `GoRoute`다 — `routes:`를 더하면 된다
- 5-2절의 자동 이동 두 개를 어떻게 막을지 (라우트 확인이든 먼저 pop이든)
- 테스트는 프로젝트 규칙대로 셋을 겨냥한다: **제목 조립**(순수 계산 — 거리 없음,
  둘뿐, 탈퇴한 대표, 긴 닉네임), **안 읽은 수 전이**(받으면 늘고 열면 0, 방이 바뀌면
  비움), 그리고 화면의 **3분기·empty**. 여기에 **채팅을 열어 둔 채 방이 죽거나
  출발 시각을 넘기는 경로**를 반드시 더한다 — 리뷰에서 나온 유일한 실제 버그 경로다
- 아이콘 PNG 두 개를 저장소로 옮기고 `pubspec.yaml`에 싣는다. 원본이 512px라
  표시 크기(24~56dp)보다 한참 크다 — 줄여서 넣을지는 빌더가 고른다
- Figma에 채팅 시안이 없다. 이 문서와 기존 화면의 토큰이 근거다
