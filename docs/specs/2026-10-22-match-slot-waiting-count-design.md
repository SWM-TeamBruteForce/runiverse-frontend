# 매칭 슬롯 대기 인원 — 설계

> 대상 API: `GET /api/v1/running-matches/slots` (1차 명세 **No 16**, BE 개발완료 · FE 개발전)
> 바뀌는 화면: 매칭 등록(**S08**) · 시간 선택 시트
>
> ⚠️ 코드 주석 두 곳이 이 API를 **14번**이라 부르고 "MVP 범위 밖"이라 적어 뒀다
> (`match_slot.dart:47`, `match_register_provider.dart:101`). **둘 다 낡았다.** 이번에 고친다.

---

## 1. 무엇을 하려는 것인가

매칭을 신청하기 전에 **"지금 이 조건에 몇 명이 기다리고 있는지"**를 보여준다. 혼자 신청해 놓고
아무 일도 일어나지 않는 것과, 세 명이 기다리는 자리에 들어가는 것은 같은 동작이지만 **누르기 전의
확신이 다르다.**

지금 앱은 그 숫자를 받을 자리(`MatchSlot.waitingCount`)만 있고 **값이 항상 `null`이다.** 조회 API가
MVP 범위 밖이라고 보고 비워 뒀는데, 그 API는 이미 개발 완료다.

### 이 작업이 사실은 두 가지다

숫자를 얹는 김에 **슬롯 목록의 주인이 앱에서 서버로 넘어간다.** 명세가 그렇게 요구한다.

> 시각 범위·간격·거리 목록은 서버 설정값입니다. **앱에서 하드코딩하지 말고 이 응답을 선택지로
> 써 주세요.** 매칭 신청이 받는 선택지와 항상 같습니다.

지금은 `MatchSlot.todayRange`가 18:00~22:00 아홉 칸을 직접 만들고 마감 여부도 **시작 시각만 보고**
정한다. 그 벽시계 비교 때문에 운영에서 **아홉 칸이 하루 종일 전부 마감으로 뜬 적이 있다**
(`match_slot.dart`의 ⚠️ 주석). 목록이 서버 것이 되면 그 계산 자체가 사라진다.

## 2. 결정한 것

사람이 정한 것과 설계자가 정한 것을 갈라 적는다.

| | 결정 | 정한 사람 |
|---|---|---|
| 시트의 줄별 숫자 | **남긴다.** 거리를 먼저 고르므로 그 거리의 시각별 수를 그릴 수 있다 | 사용자 |
| 등록 버튼 위 줄 | **거리만 골랐을 때만.** 시간까지 고르면 사라진다(4-2) | 사용자 |
| 그 줄에 적는 수 | 그 거리의 **모든 시각 합계** | 사용자 |
| 0명일 때 | **아무것도 안 그린다** — 시트 줄도, 버튼 위 줄도 | 사용자 |
| 갱신 주기 | **없다.** 폴링도 WebSocket도 아니다 | 사용자 |
| 목록의 주인 | **서버** | 사용자 |
| 화면 순서 | **거리 → 시간.** 거리를 고르기 전에는 시간을 못 고른다 | 사용자 |
| 거리 무관 합계 | **안 만든다** | 사용자 (한 번 뒤집은 결정, 10절) |
| 조회 실패 때 신청 | **막는다.** 값을 알고 고른 것이다(7-1) | 사용자 |
| `matchTimeHint` 문구 | **손대지 않는다** | 사용자 |
| 조회 시점 | 거리를 고른 순간. 거리를 바꾸거나 **같은 칩을 다시 눌러도** 다시 | 설계 |
| 상태를 어디에 | `MatchRegisterController` 하나 — provider를 새로 만들지 않는다(8-1) | 설계 |
| 조회 실패를 어디에 | `MatchFailure`가 아니라 **별도 필드**(7-3) | 설계 |
| 시각 읽기 | `KstTime.parse` — `DateTime.parse` 금지(8-5) | 설계 |
| `waitingCount` 타입 | `int?` → **`int`**(8-6) | 설계 |
| `date` 파라미터 | 안 보낸다(오늘 고정) | 설계 |

## 3. 서버가 주는 것

```
GET /api/v1/running-matches/slots?targetDistanceMeters=5000
Authorization: Bearer ...
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `date` | String | 선택. `YYYY-MM-DD`. 생략 시 오늘 |
| `targetDistanceMeters` | Integer | **필수.** 3000·5000·10000 중 하나. 해당 거리만 집계한다 |

```json
{
  "slots": [
    { "scheduledStartAt": "2026-07-25T18:00:00", "waitingCount": 0, "selectable": false },
    { "scheduledStartAt": "2026-07-25T18:30:00", "waitingCount": 3, "selectable": true }
  ]
}
```

- `slots`는 그날 신청 가능한 시각을 **빠짐없이** 담는다. 대기자가 없는 시각도 `0`으로 온다
- `waitingCount`는 **모집 중인 방의 참가자만** 센다. 확정된 방과 솔로 러닝은 빠지고, 같은 시각에
  방이 여럿이면 합산된다
- `selectable=false`는 모집 마감(**시작 10분 전**)이 지난 시각이다. 목록에 남기되 선택은 막는다.
  경계는 신청의 `MATCH_SLOT_CLOSED`와 같다

### ⚠️ 페이지 속성의 "선택"은 틀린 말이다

명세 페이지 속성에 `targetDistanceMeters는 선택`이라고 적혀 있다. **확인 결과 필수가 맞다**
(2026-10-22). 3000·5000·10000 중 하나를 반드시 골라 보낸다. 속성란 문구가 낡았을 뿐이고, 본문
표와 400 문구(`목표 거리는 필수입니다.`)가 정본이다.

**그래서 거리 없이 전체를 집계하는 길은 없다.** 10절이 그 위에 서 있다.

### 400 네 가지

| 문구 | 언제 |
|---|---|
| `입력값이 올바르지 않습니다.` | 날짜 형식이 틀렸거나 거리가 숫자가 아닐 때 |
| `목표 거리는 필수입니다.` | 거리를 안 보냈을 때 |
| `조회 날짜는 오늘 이전일 수 없습니다.` | 과거 날짜 |
| `목표 거리는 3000, 5000, 10000 중 하나여야 합니다.` | 선택지 밖 거리 |

**앱은 이 넷을 정상 경로에서 만들지 않는다.** 거리는 `TargetDistance` 셋뿐이고 날짜는 안 보낸다.
그래서 400이 오면 **앱 규칙이 서버와 어긋났다는 신호**이고, 화면에는 일반 실패로만 보인다.

## 4. 화면

### 4-1. 순서가 바뀐다

문구는 실제 `AppStrings` 값이다.

```
지금                                바뀐 뒤
┌────────────────────────┐        ┌────────────────────────┐
│ 오늘 언제 뛸까요?           │        │ 목표 거리                 │
│ [ 시간 고르기         ▾ ] │        │ (3km)(5km)(10km)       │
│ ⚡ 3명이 기다려요            │ ───▶  │                        │
│ 같은 시간대 러너끼리 매칭돼요…  │        │ 오늘 언제 뛸까요?           │
│                        │        │ [ 시간 고르기         ▾ ] │
│ 목표 거리                 │        │ 같은 시간대 러너끼리 매칭돼요…  │
│ (3km)(5km)(10km)       │        │                        │
│                        │        │ 👥 현재 3km에 7명의…        │
│ [ 매칭 등록하기 ]           │        │ [ 매칭 등록하기 ]           │
└────────────────────────┘        └────────────────────────┘
```

위 그림은 **거리만 고른 상태**다. 시간까지 고르면 `👥` 줄이 사라진다.

세 가지가 움직인다.

1. **거리가 위로 간다.** 목록을 받으려면 거리가 먼저 있어야 한다 — 화면 순서가 데이터가 흐르는
   순서와 같아진다
2. **거리를 고르기 전에는 시간 선택기가 잠긴다.** 눌러도 열 목록이 없다
3. **대기 인원 줄이 등록 버튼 바로 위로 내려오고, 말하는 내용이 바뀐다.** 지금은 시간 선택기
   아래에서 *고른 슬롯*의 수를 말하는데, 바뀐 뒤에는 *고른 거리 전체*를 말한다(4-2)

**`matchTimeHint`는 손대지 않는다.** 그 문구는 `같은 시간대 러너끼리 매칭돼요. / 대기 인원이
많을수록 빨리 만나요`이고 시각 범위를 적지 않는다 — 서버 설정값이 바뀌어도 어긋나지 않는다.

### 4-2. 숫자가 서는 자리 둘, 그리고 **서로 비킨다**

| 보는 사람의 상태 | 시트 줄별 | 등록 버튼 위 |
|---|---|---|
| 아무것도 안 고름 | — (시트를 못 연다) | 없음 |
| **거리만 고름** | 시트를 열면 시각마다 `3명 대기` | **`현재 3km에 7명의 러너가 대기중이에요`** |
| 거리 + 시간 고름 | 시트를 열면 그대로 | **없음** |

**거리만 골랐을 때 버튼 위에 서는 수는 그 거리의 모든 시각 합계다.** 응답의 `waitingCount`를 전부
더한다. "이 거리에 사람이 이만큼 있다"를 먼저 알리고, **어느 시각인지는 시트가 답한다.**

**시간까지 고르면 그 줄은 사라진다.** 고른 사람은 **시트에서 이미 그 시각의 수를 보고 골랐다** —
같은 수를 버튼 위에 한 번 더 적으면 새 정보가 없다.

**0명이면 양쪽 다 안 그린다.** 합계가 0이면 버튼 위 줄이 없고, 어떤 시각이 0명이면 그 줄에 숫자가
안 붙는다. `0명 대기`는 비어 있다고 알리는 꼴이라 오히려 사람을 민다.

#### 정본과 충돌하지 않는다

`docs/implementation-notes.md` 2-2가 *"각 슬롯에 `N명 대기`를 함께 보여준다 … 빼면 안 된다"*고
못 박아 뒀다. **거리를 먼저 고르게 되면서 시트가 그 거리의 시각별 수를 그릴 수 있어졌으므로**
그 요구가 그대로 지켜진다. 문서를 고칠 일이 없다.

(한때 시트에서 빼는 설계였다 — 12절)

마감 표시(`마감`)도 시트에 그대로 둔다.

### 4-3. 다섯 가지 상태

| 상태 | 거리 칩 | 시간 선택기 | 등록 버튼 위 줄 |
|---|---|---|---|
| 거리 전 | 고를 수 있다 | **잠김** + `거리를 먼저 골라주세요` | 없음 |
| 받는 중 | 고를 수 있다 | **잠김** + 받는 중 표시 | 없음 |
| 받았다 · 시간 전 | 고를 수 있다 | 열린다 | **합계가 1 이상이면** 보인다 |
| 받았다 · 시간까지 | 고를 수 있다 | 열린다 | **없다**(4-2) |
| **비었다** | 고를 수 있다 | **잠김** + `오늘은 신청할 수 있는 시간이 없어요` | 없음 |
| 실패 | 고를 수 있다 | **잠김** + 이유 + `다시 시도` | 없음 |

**어떤 상태에서도 거리 칩은 잠그지 않는다.** 거리를 바꾸는 것이 곧 다시 시도하는 길이다.

**"비었다"를 따로 둔 이유.** 22:00이 지나면 서버가 빈 목록을 주거나 전부 `selectable=false`를 준다.
그때 선택기만 열어 두면 시트에 `마감`만 아홉 줄이고 등록 버튼은 영영 잠긴 채라 **고장난 화면**으로
읽힌다. 고를 것이 하나도 없으면 선택기를 잠그고 이유를 적는다.

## 5. 조회 시점

**거리 칩을 누른 순간 한 번 부른다.** 거리를 바꾸면 다시 부르고, **같은 칩을 다시 눌러도 다시
부른다** — 실패했을 때 `다시 시도` 말고 그 길도 열어 둔다. 시간을 고르거나 바꾸는 것으로는 부르지
않는다. 한 번의 응답에 그날의 모든 시각이 들어 있다.

### 왜 진입 1회가 아닌가

API가 거리를 반드시 받는데 `distance`는 `null`로 시작한다. **거리가 정해지기 전에는 부를 수 있는
요청 자체가 없다.**

### 캐시하지 않는다

3km → 5km → 3km로 돌아오면 3km를 다시 부른다. 캐시하면 요청은 줄지만 **처음 받은 숫자가 그대로
남는다.** 어차피 갱신 주기가 없어서 화면에 오래 머문 사람은 낡은 숫자를 보는데, 거리를 다시 고르는
행동까지 캐시로 묶으면 **고의로 다시 확인하려는 사람에게도** 낡은 숫자를 준다.

### 겹쳐 눌러도 하나만 쓴다

칩을 빠르게 연타하면 요청이 겹친다. **나중에 고른 거리의 답만 화면에 쓴다** — 먼저 보낸 요청이
늦게 와서 덮어쓰면 칩은 10km인데 숫자는 3km가 된다. 응답을 받을 때 *지금 고른 거리*와 같은지
확인하고, 다르면 버린다(`NicknameField`의 중복확인이 같은 규칙을 쓴다).

## 6. 거리를 바꾸면 고른 시간은 어떻게 되나

**같은 `raw`의 슬롯을 새 목록에서 꺼내 통째로 갈아 끼운다.** 옛 객체를 그대로 두면 안 된다.

지금 `loadSlots()`는 "새 목록에 있고 `selectable`이면 `selected`를 그대로 둔다"(`stillOpen`)인데,
그 `selected`는 **옛 목록의 `MatchSlot` 객체**이고 `waitingCount`가 옛 거리의 값이다.

⚠️ **지금 설계에서는 그 값이 화면에 안 보인다** — 시간까지 고르면 버튼 위 줄이 사라지고(4-2),
시트는 `selected`가 아니라 목록을 읽기 때문이다. 그러니 이건 *지금 보이는 버그*가 아니라
**다음에 `selected.waitingCount`를 읽는 코드가 생기는 순간 터질 자리**다. 교체가 공짜이므로
막아 둔다 — `selectable`을 새 값으로 받기 위해서도 어차피 교체해야 한다.

| 새 목록에서 같은 `raw`가 | 결과 |
|---|---|
| 있고 `selectable` | **새 객체로 교체**한다 |
| 있지만 잠겼다 | 선택을 푼다 |
| 없다 | 선택을 푼다 |

남겨두면 마감된 슬롯으로 등록을 눌러 같은 409를 다시 맞는다.

## 7. 실패를 어떻게 다루나

### 7-1. 조회 실패 — **신청 자체를 못 한다**

이게 이 설계가 치르는 **가장 큰 값**이다. 지금은 목록을 앱이 만들어서, 서버가 죽어 있어도 시간을
고르고 등록을 눌러볼 수는 있었다. 목록이 서버 것이 되면 **받지 못하면 고를 것이 없다.**

그래도 서버로 옮기는 쪽을 골랐다(사용자 확인, 2026-10-22). 앱이 만든 목록으로 신청해도 **결국
`POST`가 서버로 가야 하므로**, 조회가 실패하는 상황에서 신청만 성공할 가능성은 낮다. 고를 수는
있는데 누르면 실패하는 화면보다 **못 고르는 이유가 적힌 화면**이 낫다.

실패하면 시간 선택기를 잠그고 그 자리에 이유와 `다시 시도`를 둔다. 거리 칩은 열어 둔다.

### 7-2. `selectable`은 **받은 시점의 사진**이다

서버가 준 `selectable=true`는 **그때** 열려 있었다는 뜻이다. 화면을 열어 둔 사이 마감(시작 10분 전)이
지날 수 있다. 그래서 `MATCH_SLOT_CLOSED`(409) 처리는 그대로 남는다.

**⚠️ 지금 코드는 409를 받아도 목록을 다시 받지 않는다.** 그 슬롯만 잠그고, 주석이 이유까지 적어
뒀다 — *"목록을 다시 받아도 앱이 만든 것이면 같은 값이 온다"*(`match_register_provider.dart:167-179`).
목록이 서버 것이 되면 그 전제가 깨지므로 **409에서 목록을 다시 받는 일을 새로 넣어야 한다.**

**앱이 시계로 다시 계산하지는 않는다.** 그러면 서버의 10분 오프셋을 앱이 알아야 하고, 그 값이
운영에서 바뀌는 날 조용히 어긋난다. 그 어긋남이 바로 이번에 지우는 코드가 겪은 일이다.

### 7-3. ⚠️ 조회 실패를 `MatchFailure`에 담지 않는다

`MatchFailure`는 **신청·취소**가 실패하는 이유를 담는 enum이고 조회 갈래가 없다. 더 큰 문제는
그것이 담기는 자리다 — `state.failure`가 차면 화면이 스낵바를 띄우고 **곧바로 `clearFailure()`를
부른다**(`match_register_page.dart:66-73`). 4-3이 요구한 "잠금 + 이유 + 다시 시도"가 한 프레임 만에
사라진다.

그래서 **조회 실패는 별도 필드**로 둔다. 스낵바가 아니라 선택기 자리에 머문다.

### 7-4. ⚠️ 신청용 에러 매핑을 그대로 쓰면 안 된다

`HttpMatchRepository.exceptionOf`는 **404를 `nothingToCancel`로 묶는다**(`http_match_repository.dart:69-71`).
취소에만 맞는 해석이다. 목록 조회에 그대로 쓰면 404에 **"취소할 활성 신청이 없어요"**가 뜬다.

조회는 자기 갈래를 갖는다.

| 갈래 | 화면 |
|---|---|
| 네트워크·타임아웃·5xx | `시간대를 불러오지 못했어요` + 다시 시도 |
| 401 | 기존 토큰 갱신 경로를 탄다. 갱신도 실패하면 세션 만료 |
| 400 | 위와 같게 보인다. **앱 규칙이 어긋났다는 신호**라 `debugPrint`로만 남긴다 |

### 8-1. 상태의 주인은 **하나**다

`MatchRegisterController`가 목록을 쥔다. **provider를 새로 만들지 않는다.** 나누면 선택 해제(6절)와

|---|---|

### 8-4. `raw`를 손대지 않는다

신청은 `slotRaw`를 그대로 돌려보낸다. 서버가 준 `scheduledStartAt` 문자열이 그대로 `raw`가 되고,
`startAt`은 **화면에 그리기 위해서만** 읽는다. 지금 규칙 그대로다.

### 8-5. ⚠️ `startAt`은 `KstTime.parse`로 읽는다

서버는 `2026-07-25T18:00:00`처럼 **오프셋 없이** 준다. `DateTime.parse`는 그걸 **기기 로컬**로
읽는다. 그런데 화면에 그리는 `AppStrings.matchSlotTime`이 `KstTime.wallOf`로 **+9시간**을 한다
(`app_strings.dart:661-667`).

둘이 겹치면 **UTC 기기에서 18:00 슬롯이 `03:00`으로 뜬다.** `KstTime.parse`가 "오프셋 없는 값은
한국 벽시계"라고 읽어 진짜 순간으로 만들어 주므로, 그것을 써야 `wallOf`와 짝이 맞는다.

### 8-5-1. 문구 둘

| 문자열 | 값 | 어디 |
|---|---|---|
| `matchWaitingCount(n)` | `3명 대기` (지금 그대로) | 시트 줄 |
| **새 문구** | `현재 3km에 7명의 러너가 대기중이에요` | 등록 버튼 위(시안 `158:3186`) |

시안 원문은 `현재 18:00에 3명의 러너가 대기중이에요`로 **시각**을 적는다. 거리를 먼저 고르게 되면서
그 자리가 **거리**로 바뀐다 — 시각은 아직 안 골랐고, 이 줄이 답하는 질문이 "이 거리에 사람이
있는가"이기 때문이다.

### 8-6. `waitingCount`가 `int?`에서 `int`가 된다

서버는 0을 포함해 **항상 숫자를 준다.** `todayRange`가 사라지면 `null`을 만드는 생산자가 없어진다.
`int?`로 남겨 두면 "0과 모름은 다르다"는 규칙이 지킬 대상 없이 떠 있고, 읽는 쪽마다 `?? 0`이 붙는다.

비널로 바꾸면 호출부가 단순해진다 — `match_register_page.dart:78`의 `?? 0`과
`match_slot_sheet.dart:154`의 `(slot.waitingCount ?? 0) > 0`이 각각 합계 계산과 `> 0`으로 줄고,
`match_slot.dart`의 "0과 모름은 다르다" 주석은 **DTO로 내려간다**(모름을 만드는 주체가 거기뿐이다).

### 8-7. 같이 죽는 것들

- **`matchClockProvider`**(`match_register_provider.dart:34`) — `todayRange`가 유일한 소비자다.
  지운다. `test/match_register_test.dart:50`의 override도 같이 지운다
- **`KstTime` import**(`match_slot.dart:1`) — `todayRange`가 사라지면 미사용이 된다. analyze 경고
  0 규칙에 걸린다
- **`MatchSlot` 클래스 상단 문서**(5~11행) — "앱이 만든 것이면"을 전제로 쓰여 있다

### 8-8. 손이 가는 자리 셋

1. **`MatchRegisterState`를 직접 생성하는 두 곳** — `loadSlots`(`:117`)와 409 분기(`:172`)가
   `copyWith`가 아니라 생성자를 쓴다. 필드를 더하면 둘 다 손대야 하고, 빠뜨리면 **받는 중 표시가
   조용히 초기화**된다
2. **`copyWith`가 `selected`를 `null`로 못 만든다**(`:76`) — 6절의 선택 해제도 직접 생성이 필요하다
3. **배너를 CTA 위로 옮기는 자리** — CTA는 `ListView` **밖** 고정 영역이다(`:184-197`).
   배너를 **고정 영역 안, CTA 바로 위**에 둔다. `ListView` 마지막 자식으로 두면 스크롤 위치에 따라
   안 보일 수 있다. 대신 배너가 나타날 때 CTA가 한 번 밀리므로, **자리를 미리 잡지 않고** 나타나게
   둔다 — 빈 자리를 늘 비워 두면 0명일 때 화면에 구멍이 남는다

### 8-9. `FakeMatchRepository`의 기본 목록

**비어 있지 않게 둔다.** 빈 목록이 기본이면 등록 화면 테스트마다 목록을 직접 주입해야 한다.

다만 **18:00~22:00을 fake에 하드코딩하지 않는다.** 그러면 앱이 그 값을 다시 갖게 되고, 이번 작업이
없애려던 것이 테스트 쪽으로 옮겨갈 뿐이다. 임의의 시각 서넛(예: `10:00` · `10:30` · `11:00`)을
쓴다 — **운영값과 일부러 다르게** 둬서, 앱 어딘가가 18:00~22:00을 전제하면 테스트가 깨지게 한다.

## 9. 테스트

CLAUDE.md가 정한 세 가지(순수 계산 · 결정론 · 상태 전이)에 맞춰 둔다.

**DTO**
- `scheduledStartAt`·`waitingCount`·`selectable`을 읽는다
- ⚠️ **`KstTime.parse`로 읽는다** — 기기 시간대를 UTC로 두고 `18:00`이 `18:00`으로 그려지는가(8-5)
- `waitingCount: 0`이 빠지지 않는다
- 빈 `slots`도 실패가 아니다

**상태 전이**
- 거리를 고르면 그 거리로 한 번 부른다
- 거리를 바꾸면 다시 부른다. **시간을 바꾸면 안 부른다**
- 같은 거리 칩을 다시 눌러도 부른다
- ⚠️ 느리게 온 앞 요청이 **나중 거리의 답을 덮지 않는다**
- ⚠️ **거리를 바꾸면 `selected`가 새 목록의 같은 `raw`로 교체된다** — 옛 `waitingCount`가 남지
  않는가(6절)
- 고른 시간이 새 목록에 없거나 잠겼으면 선택이 풀린다
- 실패하면 목록이 비고 이유가 남는다. ⚠️ **스낵바로 사라지지 않는다**(7-3)
- 409를 받으면 목록을 다시 받는다(7-2)

**화면**
- 거리 전에는 시간 선택기가 잠겨 있다
- 빈 목록이면 선택기가 잠기고 이유가 보인다
- ⚠️ **거리만 골랐을 때** 등록 버튼 위에 **합계**가 선다 — 한 시각의 수가 아니라 전부 더한 값인가
- ⚠️ **시간까지 고르면 그 줄이 사라진다**(4-2)
- 합계가 0이면 그 줄이 아예 없다
- 시트는 시각마다 그 거리의 수를 그린다. 0인 시각에는 숫자가 안 붙는다

### 9-1. 깨지는 테스트

**`test/match_register_test.dart` — 거의 전부.** 8곳(`:126 :136 :195 :207 :222 :240 :255 :272`)이

## 10. 가는 길에 한 번 뒤집힌 것

처음에는 **시간 선택 시트의 줄마다 "거리 무관 합계"**를 띄우기로 했다. 그러려면 3000·5000·10000을
**세 번 불러 더해야 한다** — API가 거리를 반드시 받고, 준 거리만 집계하기 때문이다.

그 설계의 값이 컸다. 진입마다 요청 셋이 나가고, 따로 도착해 합계가 중간값으로 깜빡이고, **하나만
실패하면 합계가 조용히 작아진다.** 작아진 숫자는 "대기자가 적다"로 읽혀 사용자를 다른 슬롯으로
민다 — 틀린 방향으로 조용히 미는 것이 가장 나쁜 실패다.

그래서 **고른 조합 하나만** 보여주는 쪽으로 바꿨다. 요청이 하나로 줄고, 합산이 없어지니 부분 실패도
없다.

거리가 선택 파라미터였다면 한 번만 불러 합계를 받을 수 있어 다른 선택지가 있었겠지만, **필수임이
확인됐다**(3절). 되돌릴 길은 서버가 "거리 생략 시 전체 합계"를 새로 열어 주는 경우뿐이다.

## 12. 이 문서가 한 번 고쳐진 자리

빌더 검토(2026-10-22)가 **설계 결함 하나와 사실 오류 넷**을 찾아냈다.

**결함** — 거리를 바꿀 때 `selected`를 옛 객체로 두면 배너에 **옛 거리의 대기 인원**이 남는다.
10절이 "가장 나쁜 실패"로 꼽은 것을 설계가 그대로 재현하고 있었다. 6절을 "같은 `raw`로 교체"로
고쳤다.

**사실 오류**
- *"409를 받으면 목록을 다시 받는다 — 지금 코드가 이미 그렇게 한다"* → **안 한다.** 새로 넣어야
  하는 일이다(7-2)
- *`18:00~22:00` 안내 문구* → **그런 문구가 없다.** 열린 질문 하나가 없는 대상을 겨누고 있었다
- 화면 번호 `S10` → **`S08`**, 다이어그램 문구도 실제 `AppStrings` 값으로
- `startAt`을 `DateTime.parse`로 읽어도 된다는 전제 → **`KstTime.parse`여야 한다.** 그대로 두면
  UTC 기기에서 18:00이 `03:00`으로 뜬다(8-5)

같은 검토에서 상태의 주인(8-1) · 조회 실패를 담는 자리(7-3) · 신청용 에러 매핑 재사용의 함정(7-4) ·
`waitingCount` 비널화(8-6) · 같이 죽는 것들(8-7) · fake의 기본 목록(8-9) · 깨지는 테스트 범위(9-1)도
함께 못 박았다.

### 그리고 숫자가 서는 자리가 두 번 바뀌었다

1. 처음: 시트 줄마다 **거리 무관 합계** + 버튼 위에 고른 슬롯의 수
2. 다음: 시트에서 **빼고** 버튼 위 한 곳에만 (여기서 `implementation-notes.md` 2-2와 충돌했다)
3. 지금: **시트에 줄별로 남기고**, 버튼 위는 **거리만 골랐을 때 그 거리의 합계**

3번이 앞의 둘을 동시에 푼다. 거리를 먼저 고르게 되면서 시트가 그 거리의 시각별 수를 그릴 수
있어져 정본과 충돌이 사라지고, 버튼 위 줄은 **시트가 답하지 못하는 질문**("이 거리에 사람이
있는가")만 맡아 중복이 없다. 시간까지 고르면 그 질문이 끝나므로 줄도 사라진다.

**열린 질문은 없다.**
