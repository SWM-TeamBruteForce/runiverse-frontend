### 화면 꺼짐 대응 `[2026-08-27 추가]`

**"앱이 화면에 떠 있을 때만 추적한다"는 전제가 없어졌다.** 포그라운드 서비스를
띄우므로 화면을 꺼도, 다른 앱으로 넘어가도 좌표가 계속 들어온다.

없을 때 무엇이 문제였나 — 화면이 꺼지면 Android가 위치 갱신을 시간당 몇 번으로
제한한다. 그 구간이 좌표 공백이 되고, **서버는 빈 자리를 직선으로 이어 거리를
실제보다 짧게 계산한다.** 뛴 만큼 기록이 안 나오는 것은 되돌릴 수 없다.

`ACCESS_BACKGROUND_LOCATION`은 **넣지 않는다.** Android가 보는 것은 화면이
켜져 있는지가 아니라 **서비스를 시작하는 순간 앱이 포그라운드였는지**다.
사용자가 화면을 보며 시작을 누르므로 해당이 없다. 넣으면 사용자가 설정 화면에
직접 들어가 "항상 허용"을 골라야 하고 Play 심사 부담이 커진다.

**여기서 딸려 나오는 것 셋**

| | 무엇 |
|---|---|
| 알림 권한 | Android 13+에서 `POST_NOTIFICATIONS`를 런타임으로 받아야 알림이 보인다. **못 받아도 서비스와 좌표는 정상이다** — 서랍에 안 보일 뿐 |
| Play 심사 | 포그라운드 서비스 선언서와 시연 영상이 필요하다. 백그라운드 위치 선언과는 다른 제도고 가볍다 |
| 종료 정리 | 러닝을 끝낼 때 위치 구독을 끊어야 서비스가 내려간다. 안 끊으면 개발 중에는 안 보이고 **사용자가 배터리로 먼저 알아챈다** |

세 번째는 `RunSessionController._teardown()`이 이미 한다 — `finish()`·`reset()`·
`onDispose`가 전부 그것을 부른다. 다만 **실기기로 눈으로 봐야 확실하다.**

⚠️ **에뮬레이터로는 검증할 수 없다.** 화면 끔 동작이 실기기와 다르다.

### 앞으로의 작업에 바뀌는 것 `[2026-08-27]`

**① 전송 타이머가 화면 꺼짐을 견디는지 확인해야 한다** — WS 설계 4단계

`TrackSender`가 `Timer.periodic(10초)`로 좌표를 올린다. 포그라운드 서비스가
CPU를 깨워 두므로 계속 돌 것으로 보지만, **확인한 적이 없다.** 눌리면 배치가
쌓였다가 재개 시 몰려 나가고, 한 메시지 상한이 200점이라 긴 화면 꺼짐 뒤에는
여러 틱에 걸쳐 따라잡는다. 실기기 확인 항목에 넣는다.

**② 경과 시간은 영향을 받지 않는다** — 이미 안전하다

`_elapsed()`가 틱 수를 세지 않고 `_now().difference(resumedAt)`로 잰다.
타이머가 눌려도 시간은 어긋나지 않는다. 화면 갱신만 늦어진다.

**③ `_lastSent` 커서를 메모리에 두는 판단이 더 안전해졌다**

프로세스가 죽으면 커서가 사라지는 것이 이 결정의 약점이었는데, 포그라운드
서비스가 뜬 동안에는 시스템이 프로세스를 잘 죽이지 않는다. **DB 컬럼으로
옮길 이유가 줄었다.**

**④ 알림 권한을 언제 물을지 정해야 한다** — TMB-169

`POST_NOTIFICATIONS`는 푸시와 로컬 알림을 함께 덮고 **두 번 거절하면 영구
거절**이다. 앱을 켜자마자 묻으면 맥락이 없어 거절당하기 쉽고, 그러면 나중에
푸시를 붙일 때 물어볼 기회가 없다.

**러닝 시작 직전이 가장 맥락이 분명하다** — 곧 알림이 뜰 참이고, 사용자는
그것이 무엇인지 안다. 다만 카운트다운 3초를 이미 연결 창으로 쓰고 있어
그 앞에 다이얼로그를 하나 더 끼우는 것이 맞는지는 따로 봐야 한다.

**⑤ 제조사 배터리 최적화는 별개 문제다**

삼성·샤오미 등은 포그라운드 서비스도 공격적으로 정리한다. 표준 동작이 아니라
기기마다 다르고, 앱이 할 수 있는 것은 설정으로 안내하는 것뿐이다. 실기기에서
증상이 나오면 그때 다룬다.

```
홈 (S05 상태1)
 │

 │
 └─ [혼자 달리기]
      │
      ▼
   권한 확인 ──거부──► 설정 안내 시트 ──► 홈
      │ 허용
      ▼
   출발 준비  ← GPS 첫 신호를 잡을 때까지 시작 버튼 잠금
      │ [시작]
      ▼
    3 · 2 · 1   ← 되돌아갈 수 없는 구간
      │
      ▼
   러닝 진행 ◄──┐
      │ [중지]  │ [계속 달리기]
      ▼        │
   중지 시트 ───┘
      │ 길게 눌러 종료 (2초)
      ▼
```

### 2-1. 왜 출발 준비 화면을 두는가

정본 S11의 컴포넌트 리스트에 이렇게 적혀 있다.

> GPS 인디케이터: 최우선(러닝 실패 예방)

GPS는 앱을 켜자마자 위치를 알지 못한다. 위성을 잡는 데 실내에서는 수십 초가 걸리고,
그 전에 출발하면 **초반 거리가 통째로 빠진다.** 사용자는 자기가 뛴 만큼 기록이 안 나온
이유를 알 수 없다.

그래서 첫 신호를 받기 전에는 시작 버튼을 잠그고, 잠긴 이유를 글로 보여준다.
색만으로 알리지 않는다 (정본 C9 — 상태는 색 단독 금지).

### 2-2. 3·2·1 구간에는 뒤로가기가 없다

정본 S11이 그렇게 정했다(취소 불가 구간). 1인 러닝도 같게 둔다.
카운트다운 도중에 빠져나갈 수 있으면 "시작됐는가"의 판정이 두 곳으로 갈린다.

## 3. 좌표를 칼만 필터로 보정한다 `[2026-08-25 변경]`

**제자리에 서 있어도 거리가 늘어난다.**

GPS 좌표는 가만히 있어도 몇 미터씩 흔들린다. 받은 좌표를 그대로 이어 붙이면
그 흔들림이 전부 거리가 된다. 신호가 나쁜 실내에서는 서 있는 채로 분당 수십 미터가 쌓인다.

처음에는 보정을 미뤘다. 이제 넣는다.

### 3-1. 1차원 칼만 필터를 위도·경도에 각각 건다

```
예측   p = p + Q
이득   K = p / (p + R)
갱신   x = x + K·(z − x)
       p = (1 − K)·p
```

`x`는 추정값, `p`는 그 추정을 얼마나 믿는지, `z`는 방금 받은 측정값이다.

| | 무엇으로 정하나 | 값 |
|---|---|---|
| `R` 측정 노이즈 | 좌표의 **정확도** | `< 5m` → 0.01 · `5~10m` → 0.05 · `> 10m` → 0.1 |
| `Q` 프로세스 노이즈 | 그 순간의 **속도** | `< 1` → 0.005 · `1~3` → 0.01 · `3~6` → 0.02 · `> 6` → 0.05 |

정확도가 나쁘면 `R`이 커지고, `R`이 커지면 `K`가 작아져 **그 측정값을 덜 믿는다.**
빠르게 달릴수록 `Q`가 커져 위치가 실제로 변한다는 것을 받아들인다.

> 값의 출처는 iOS `CLLocation` 보정 사례다(제자리 오차 86% 감소).

한 자리에서 5m씩 흔들리는 좌표 120개를 먹여 본 결과다. 실기기가 아니라 **합성 잡음**이다.

| 좌표 정확도 | 누적 거리 | 감소 |
|---|---|---|
| 3m | 508m → 213m | 58% |
| 8m | 508m → 112m | 78% |
| 20m | 508m → 83m | 84% |

정확도가 나쁠수록 많이 줄어든다 — `R`이 커져 그 좌표를 덜 믿기 때문이고, 반대로
좋은 좌표를 세게 누르면 진짜 이동까지 깎인다.

> ⚠️ **실기기에서 검증하지 않았다.** 합성 잡음은 실제 GPS의 편향(한쪽으로 쏠렸다
> 돌아오는 성질)을 흉내 내지 못한다. 값 조정은 실측 뒤에 한다.

### 3-2. 임계값으로 점을 버리지 않는다

앞선 판에서는 규칙 셋(정확도가 나쁜 점·너무 가까운 점·불가능한 점프를 버린다)을 예고했다.
**넣지 않기로 했다.**

버릴지 말지의 판단을 `R` 하나가 연속적으로 대신한다 — 나쁜 점은 버려지는 대신 약하게
반영된다. 임계값을 세우면 그 값을 실기기에서 정해야 하고, 경계 근처에서 점이 통째로
사라져 경로가 끊긴다.

칼만만으로 모자라다는 것이 실기기에서 드러나면 그때 더한다.

### 3-3. 보정된 좌표 하나만 흘려보낸다

```
LocationRepository.watchPosition()
        │  원본 GeoPoint
        ▼
   LocationSmoother          ← 칼만 필터 두 개(위도·경도)
        │  보정된 GeoPoint
        ▼
RunSessionController._onPoint()  ──►  누적 거리 · 지도 경로
```

**거리 계산과 지도가 같은 좌표를 본다.** 원본으로 선을 그리고 보정값으로 거리를 세면
화면의 선과 화면의 숫자가 서로 다른 이야기를 한다.

속도는 `GeoPoint`가 실어 나른다 — 직전 점과의 거리로 계산할 수도 있지만, 센서가 주는
값(도플러 기반)이 더 정확하고 이미 `accuracy`를 같은 방식으로 받고 있다.

## 4. 레이어

```
features/session/
  domain/                          순수 Dart. 패키지를 모른다
    geo_point.dart                 위도 · 경도 · 시각 · 정확도
    run_metrics.dart               거리 · 경과시간 · 현재페이스 · 평균페이스
    run_session_state.dart         sealed — 준비 / 진행 / 일시정지 / 종료
    pace_calculator.dart           거리 + 시간 → 페이스
    location_repository.dart       인터페이스

  data/
    geolocator_location_repository.dart
    fake_location_repository.dart  좌표를 손으로 먹인다

  presentation/
    run_session_provider.dart
    run_prepare_page.dart
    run_session_page.dart
    run_summary_page.dart
```

### 4-1. `domain/`이 geolocator를 모르게 둔다

geolocator가 주는 `Position`을 화면까지 들고 가지 않는다. 받는 즉시 `GeoPoint`로 옮긴다.

이유는 둘이다.

- **테스트.** 거리·페이스 계산을 실기기 없이 돌릴 수 있다. `GeoPoint` 목록을 손으로 만들면 된다
- **교체.** 패키지를 바꿔도 `data/` 파일 하나만 다시 쓴다

인증에서 `AuthRepository` 하나에 `FakeAuthRepository`를 끼운 것과 같은 구조다.

### 4-2. 세션 상태는 `keepAlive`다

`implementation-notes.md` §5-1에 적힌 함정이다. **숨은 탭의 provider는 실제로 dispose된다.**
러닝 중에 다른 화면이 위로 올라오면 상태가 통째로 사라진다.

그리고 `ref.onDispose`에서 위치 구독을 반드시 끊는다. 안 끊으면 러닝이 끝나도
GPS가 계속 돌아 배터리를 먹는다.

### 4-3. 화면은 필요한 값만 본다

러닝 화면은 **초당 여러 번** 갱신된다. 상태 전체를 `watch`하면 그때마다 화면 전체가 다시 그려진다.
숫자 한 칸은 자기 숫자만 `select`한다.

## 5. 케이던스와 칼로리는 자리만 둔다

정본 S13의 2×2 그리드는 시간 · 거리 · 케이던스 · 칼로리 넷이다.
레이아웃은 그대로 두되 뒤의 둘은 `--`로 표시한다.

| 지표 | 필요한 것 | 지금 상태 |
|---|---|---|
| 케이던스 | 가속도계 센서 · 걸음 검출 | 센서를 안 읽는다 |
| 칼로리 | 사용자 체중 | 프로필에 체중 항목이 없다 |

지어낸 값을 넣지 않는다. 러닝 기록은 사용자가 믿고 보는 숫자다.
`--`는 "아직 없다"를 정직하게 말한다.

## 7. 패키지 두 개

| 패키지 | 대안 | 고른 이유 |
|---|---|---|
| `geolocator` | `location` | 권한 요청 · 설정 앱 열기 · 거리 계산이 한 패키지에 있다. `location`은 `permission_handler`를 따로 붙여야 한다 |
| `wakelock_plus` | 없음 | Flutter에 화면을 켜 두는 내장 수단이 없다 |

`wakelock_plus`는 "포그라운드만 추적한다"는 결정의 필연적 결과다.
화면이 꺼지면 추적이 멈추므로, 달리는 동안에는 화면을 켜 둬야 한다.
러닝을 끝내면 반드시 해제한다 — 안 하면 앱을 나가도 화면이 안 꺼진다.

`AndroidManifest.xml`에 `ACCESS_FINE_LOCATION` · `ACCESS_COARSE_LOCATION`을 선언한다.

### 7-1. 지도 `[2026-08-25 추가]`

| 패키지 | 대안 | 고른 이유 |
|---|---|---|
| `flutter_naver_map` | `google_maps_flutter` | 국내 도보 경로·지형 표현이 낫다. 구글은 국내 데이터 반출 제약으로 표현이 제한된다 |

Client ID는 **`--dart-define=NAVER_MAP_CLIENT_ID=...`로 받는다.** 코드에 적지 않는다.

⚠️ **키가 없으면 SDK를 초기화하지 않는다.** 없는 키로 초기화하면 앱이 통째로 죽는다 —
카카오 로그인에서 겪은 것과 같은 함정이다(`implementation-notes.md` §9-1). 키가 비면
지도 자리에 안내를 그리고 나머지 기능은 그대로 돌린다.

### 7-2. FusedLocationProviderClient를 명시한다 `[2026-08-25 추가]`

geolocator는 Android에서 이미 `FusedLocationProviderClient`를 쓴다(`forceLocationManager`
기본값이 `false`다). 다만 공통 `LocationSettings`를 쓰면 그 사실이 코드에 드러나지 않고,
누군가 `true`로 바꿔도 아무것도 막지 않는다. `AndroidSettings`로 바꿔 못 박는다.

## 8. 테스트

CLAUDE.md가 정한 세 갈래 중 둘에 해당한다.

**순수 계산**

- 두 좌표 사이의 거리
- 좌표 목록의 누적 거리
- 거리 + 시간 → 페이스 환산 (0으로 나누기 포함)
- 페이스 표기 — `5'32"` 형식

**상태 전이**

- `준비 → 진행 → 일시정지 → 진행 → 종료`
- 일시정지 중에는 경과 시간이 늘지 않는다
- 일시정지 중에 들어온 좌표는 거리에 더하지 않는다
- 종료하면 위치 구독이 끊긴다

시간이 걸리는 판정은 **시계를 주입해서** 확인한다. 인증의 5분 만료를 확인한 방법과 같다.
실제로 5분을 기다리지 않는다.
