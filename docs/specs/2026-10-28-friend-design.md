# 친구 맺기 — 요청하고 수락한다 (설계)

> 작성 2026-10-28 · 백엔드 7개 엔드포인트 개발완료, 프론트 개발전
> 시안 — 목록·검색 `79:2081`, 프로필 `85:2882`
> 웹뷰 시안 — https://claude.ai/artifact/VWyANyCJaKBhsGNrhwbUQ7

러너끼리 **친구**를 맺는다. 한쪽이 요청하고 다른 쪽이 수락해야 성립하는
**양방향** 관계다.

## 2. 쓰는 엔드포인트

| No | 메서드 | 경로 | 쓰는 곳 |
|---|---|---|---|
| 40 | POST | `/users/{userId}/friend-request` | 친구 요청 |
| 41 | PUT | `/users/{userId}/friend-request` | 수락 |
| — | DELETE | `/users/{userId}/friend-request` | 취소 · 거절 (하나다) |
| 43 | DELETE | `/users/{userId}/friend` | 친구 삭제 |
| 42 | GET | `/users/{userId}/friends` | 친구 탭 · 타인의 친구 목록 |
| — | GET | `/users/me/friend-recommendations` | 추천 탭 |
| 44 | GET | `/users/search` | 검색 |
| **38** | GET | `/users/{userId}` | 프로필 요약 — **이미 쓰고 있다** |

No 38은 `userId` · `isMe` · `nickname` · `profileImageUrl` · `introduction` ·
`friendCount` · `friendStatus` 일곱을 준다. **개발완료**이고, 앱의
`http_profile_repository.dart`가 이미 부르면서 `friendCount`까지 읽고 있다.
`isMe`와 `friendStatus`만 아직 안 읽는다. 마일리지·러닝 횟수 같은 지표는 이
응답에 **없다** — 그래서 프로필 스탯은 `친구`와 `업적` 두 줄이 전부다.

`DELETE /friend-request`와 `friend-recommendations`는 명세에 번호가 없지만 둘 다
`BE 현황: 개발완료`다.

### 2-1. ⚠️ 관계를 부르는 말이 서버에 둘 있다

친구 엔드포인트는 `relationshipType`, 프로필 요약(No 38
`GET /users/{userId}`)은 `friendStatus`인데 **값까지 다르다.**

| 뜻 | 친구 API `relationshipType` | 프로필 API `friendStatus` |
|---|---|---|
| 관계 없음 | `NONE` | `NONE` |
| 내가 보냄 | `FRIEND_REQUEST_SENT` | `PENDING_SENT` |
| 내가 받음 | `FRIEND_REQUEST_RECEIVED` | `PENDING_RECEIVED` |
| 친구 | `FRIEND` | `ACCEPTED` |

**앱의 enum은 하나다.** 읽는 쪽에서 두 어휘를 모두 받아 같은 값으로 접는다.
한쪽만 읽으면 타인 프로필의 버튼이 통째로 틀린다.

둘 다 **조회하는 사람 기준**이고, 대상이 나 자신이면 `null`이다.

### 2-2. 서버가 보장하는 것, 보장하지 않는 것

**보장한다**

- `friends`는 **받은 요청 → 보낸 요청 → 친구** 순으로 묶어서 준다. 묶음 안은
  관계가 바뀐 최근순이다.
- 추천은 **친구·요청이 오간 사람·나 자신·온보딩 전인 사람을 빼고** 준다.
  그래서 추천 목록은 전부 `NONE`이다.
- 서로 요청하면 수락 없이 바로 친구가 된다(POST가 `200` + `FRIEND`).
- 수락(PUT)은 멱등이다. 이미 친구면 같은 응답을 준다.

**보장하지 않는다**

- **실시간 반영이 없다.** 내가 보낸 요청을 상대가 수락해도 앱은 모른다
  (명세: SSE 추후 지원). **인앱 알림을 백엔드가 만들고 있다**(2026-10-28 확인).
- **검색 결과는 닉네임 오름차순뿐이다.** 관계별 정렬이 없다.
- **취소·거절·삭제는 멱등이 아니다.** 두 번 부르면 `404`다.

## 3. 화면 넷

```
프로필 탭 ──(친구 · N)──▶ 친구 화면 ──(행 탭)──▶ 타인 프로필
                          ├ 친구 탭
                          ├ 추천 탭
                          └ 검색(탭 접힘)
```

새 화면은 **친구 화면 하나**다. 프로필 탭과 타인 프로필은 이미 있는 화면에
줄을 더한다.

### 3-1. 진입점 — 프로필의 `친구 · N`

시안 `85:2882`의 **팔로워 자리**(x=14, y=360)에 들어간다. 아이콘은 팔로우 행이
쓰던 사람 글리프(`assets/icons/people.svg`), 글자는 `친구 · 12`다.

- 양방향이라 팔로워·팔로우 두 줄이 **한 줄**이 된다.
- 받은 요청이 있으면 숫자 옆에 **빨간 배지**가 붙는다.
- 둘째 줄은 `업적` + `준비중`이다. 컬러 행은 뺐고, 업적은 **다음 업데이트**
  몫이라 눌리지 않는다. 그 아래 `러닝 업적 준비중` 실루엣(항목별 진행률 막대 +
  다음 단계 깃발)을 흐리게 깔아 둔다.
- 컬러도감·뱃지도감 탭 줄은 보여 줄 것이 없어 **뺐다.**

**탭을 새로 만들지 않는다.** 하단 탭은 홈·기록·기록카드·프로필 넷으로 고정이고
(`CLAUDE.md` Scope), 와이어프레임도 "독립 탭 아님 — 프로필에서 진입"으로 못
박았다. 지금 프로필 화면은 닉네임 아래가 통째로 비어 있어 자리를 뺏지 않는다.

### 3-2. 친구 화면 — 검색창 고정 + 탭 둘

시안 `79:2081`의 구조를 그대로 쓴다.

```
‹  [🔍 닉네임으로 찾기            ]
─────────────────────────────────
     친구          │      추천
 ━━━━━━━━━━        │
```

치수(시안값): 좌우 여백 14 · 검색창 radius 12, padding 16/14 · 탭 밑줄 2px,
너비 85 · 행 높이 62 · 아바타 48(radius 100) · 버튼 97×40, radius 12,
border 0.6px.

**시안에서 뺀 것 셋**

- `정렬` — `friends`에 정렬 파라미터가 없다. 서버 정렬이 이미 "내가 답해야 할
  것이 먼저"다.
- `온라인` · `최근 접속 5분전` — 접속 상태를 주는 API가 없다. 그 자리는 추천
  탭에서 **추천 이유**가 받는다.
- `팔로워` / `팔로잉` 탭 — 양방향이라 두 목록이 같다. `친구` / `추천`으로
  바꿨다.

### 3-3. 친구 탭 — 탭이 아니라 섹션

받은 요청 · 보낸 요청 · 친구를 **한 목록**에 섹션 머리만 얹어 세로로 편다.

⚠️ **세그먼트 탭으로 쪼개면 안 된다.** `friends`가 셋을 한 목록에 담아 커서로
넘긴다. 탭마다 따로 받을 파라미터가 없고, 커서는 목록 하나 기준이라 섞으면
`400`이다.

### 3-4. 추천 탭 — 버튼이 하나뿐이다

서버가 친구·요청 중인 사람을 빼고 주므로 전부 `NONE`이다. 버튼은 `친구 요청`
하나이고, 누르면 그 자리에서 `요청됨`으로 바뀐다. 다음에 열면 목록에서 빠져
있다.

시안의 상태 점 자리에 추천 이유를 쓴다.

| `reason` | 문구 | 점 색 |
|---|---|---|
| `RAN_TOGETHER` | `최근에 함께 뛴 러너` | `primary` |
| `SIMILAR_PACE` | `나와 페이스가 비슷한 러너` | `success` |

페이지가 없다(최대 30명). 상대의 페이스 값은 안 내려온다.

### 3-5. 검색 — 탭이 접힌다

검색창에 글자가 들어가면 **탭이 접히고** 결과 목록만 남는다. `✕`를 누르면
탭이 돌아온다.

검색은 탭과 무관하게 **전체 사용자** 하나다(`/users/search`). 친구를 찾는 일도
결과 맨 위 `친구` 묶음이 받아 주므로 **`friends?q=`는 쓰지 않는다** — 친구가
아주 많아져 목록 안에서 추려야 할 때 꺼낸다.

결과는 관계별로 묶고, 순서는 **이미 맺은 것이 위**다.

```
친구          → ⋯ (친구 삭제)
받은 요청     → 수락 · 거절
보낸 요청     → 요청 취소
그 밖의 러너  → 친구 요청
```

### 3-6. 타인 프로필 — 내 프로필과 같은 틀

커버 200 · 아바타 86 · 스탯 두 줄 · 업적 실루엣까지 같다. 다른 건 둘뿐이다.

| | 내 프로필 | 타인 프로필 |
|---|---|---|
| 우상단 | 프로필 편집 | **관계별 버튼** |
| 좌상단 | 종 · 설정 | 뒤로 |

친구 수를 누르면 **그 사람의 친구 목록**으로 간다. 타인 목록에는 친구만
담기므로 탭도 섹션도 없는 한 줄 목록이다.

## 4. 관계별 버튼

| `relationshipType` | 친구 탭 · 검색 결과 | 추천 | 프로필 | 부르는 것 |
|---|---|---|---|---|
| `FRIEND` | `⋯` → 친구 삭제 | 안 옴 | 친구 ▾ → 삭제 | `DELETE /friend` |
| `FRIEND_REQUEST_RECEIVED` | 수락 · 거절 | 안 옴 | 수락 · 거절 | `PUT` / `DELETE /friend-request` |
| `FRIEND_REQUEST_SENT` | 요청 취소 | `요청됨`(누른 직후만) | 요청 취소 | `DELETE /friend-request` |
| `NONE` | 친구 요청 | 친구 요청 | 친구 요청 | `POST /friend-request` |
| `null` (나) | — | 안 옴 | 프로필 편집 | — |

**친구 삭제는 `⋯` 뒤에 숨기고 확인 다이얼로그를 붙인다.** 되돌릴 수 없는 동작이
목록에 그대로 노출되면 손이 스친다.

### 4-1. 누른 뒤 목록을 다시 읽지 않는다

응답으로 그 행의 `relationshipType`만 바꾼다.

- 요청 · 수락 → 응답의 `relationshipType`을 그대로 쓴다.
- 취소 · 거절 · 삭제 → `204`라 본문이 없다. `NONE`으로 바꾼다.
- 받은 요청을 수락하면 **다시 불러오지 않고** 그 항목을 친구 묶음 맨 위로
  옮긴다(명세 권고).

### 4-2. ⚠️ 요청이 `200`으로 올 수 있다

상대가 이미 나에게 요청해 뒀으면 POST가 `201`이 아니라 **`200` + `FRIEND`**를
준다. 상태 코드로 분기하지 말고 **응답의 `relationshipType`을 그대로 믿는다.**

### 4-3. 실패를 어떻게 말하나

| 코드 | 언제 | 화면 |
|---|---|---|
| `404` | 이미 취소·거절됨, 상대 탈퇴, 경합에서 짐 | 그 행을 `NONE`으로 되돌리고 "이미 처리된 요청이에요" |
| `409` `FRIEND_REQUEST_ALREADY_EXISTS` | 이미 요청했거나 이미 친구 | 그 행을 다시 읽어 맞춘다 |
| `400` `CANNOT_FRIEND_SELF` | 나 자신 | **일어나면 앱 버그다.** 검색·추천·목록 모두 나를 빼고 준다 |
| 그 밖 | 네트워크 등 | 스낵바 한 줄, 버튼은 원래대로 |

## 5. 검색 결과를 읽는 방법

**묶는 건 앱이 한다.** 서버는 닉네임 오름차순으로만 준다.

⚠️ **묶음 안에서는 서버가 준 닉네임 순서를 지킨다.** 그래야 나중에 받은 사람이
자기 묶음 **끝**에만 붙고, 이미 그려진 행 사이로 끼어들지 않는다.

| 언제 | 부르는 것 | 화면 |
|---|---|---|
| 검색어를 넣는다 | `q=…&limit=20` | 20개를 묶어서 표시 |
| 바닥 가까이 스크롤 | `q=…&limit=50` | 50개로 통째 교체 |
| 그 이상 | 없음 | 50개가 상한 |

**커서를 쓰지 않는다.** 명세가 "페이지를 넘기는 사이에 닉네임을 바꾼 사람은
빠지거나 한 번 더 내려올 수 있다"고 경고하는데, 같은 `q`로 한 번 더 받으면 그
구간 자체가 없다. 앞 20개를 다시 받는 비용은 네 필드짜리 행 스무 개다.

50을 넘기는 닉네임 검색은 그 자체로 더 좁혀야 할 검색이라, 커서는 필요해지면
그때 붙인다.

**친구 탭은 커서를 쓴다.** 거기는 내 친구 전부가 대상이라 50에서 끊을 수 없다.
`nextCursor`를 그대로 돌려보낸다(내용을 해석하지 않는다).

## 7. 범위 밖

- **업적** — 다음 업데이트. 이번에는 `준비중` 실루엣만 그린다.
- **초대 러닝** — 홈의 `친구랑 뛰기`를 `초대 러닝`으로 바꾸는 작업은 별건이다.
  친구 목록을 쓰게 되지만 이번 범위가 아니다.
- **인앱 알림** — 백엔드가 만들고 있다. 그게 오기 전까지 받은 요청은 프로필
  빨간 숫자로만 알리고, 그 숫자는 **화면을 열 때** 갱신된다.
- **타인의 친구 목록** 화면은 만들되 커서·검색은 붙이지 않는다(친구만 오고 수가
  적다).

## 8. 열려 있는 것

### 8-1. 받은 요청에 "최근에 함께 뛴 러너"를 못 붙인다

`friends` 응답에 그 정보가 없고, 추천 API는 **요청이 대기 중인 사람을 아예
빼서** 교차 조회도 안 된다. 앱이 직접 알아내려면 과거 방 명단을 방마다 받아야
해서 요청이 사람 수만큼 붙는다.

→ **백엔드에 `friends` 응답 항목의 선택 필드로 `reason`을 요청한다.** 받는 쪽이
"누군지 모르겠는 요청"을 판단할 근거가 생기는 게 이 기능의 값어치다. 화면은 그
자리를 이미 비워 뒀으므로 필드가 생기면 그대로 채워진다.

### 8-2. 팔레트가 둘이다

시안은 `#0A0A0A` 바탕에 `#227DFF`, 앱 토큰은 `#0B0E14`에 `#5B8CFF`다. 이 설계는
**앱 토큰**으로 간다. 어느 쪽으로 맞출지는 친구 화면만의 문제가 아니라 앱 전체
문제라 따로 정한다.

### 8-3. 검색 결과 50 상한

닉네임 부분 일치로 50명을 넘기면 더 못 본다. 실제로 걸리면 커서를 붙인다.

## 9. 검토에서 정한 것

설계를 처음 보는 엔지니어에게 읽혀(2026-10-28) 나온 물음을 여기서 닫는다.

### 9-1. 명세를 다시 읽어 답한 것

- **검색 파라미터는 `q` · `cursor` · `limit`이다.** `limit` 기본 20, 최소 1,
  50을 넘으면 50으로 줄인다. `q`는 **닉네임 부분 일치**, 최대 16자, 앞뒤 공백
  무시, `%`·`_`는 글자 그대로다. §5가 선 땅이 확인됐다.
- **검색에 나는 안 나온다.** 명세가 "나 자신은 결과에 나오지 않는다"고
  못 박는다. 온보딩 전·탈퇴자도 안 나온다. 그래서 `CANNOT_FRIEND_SELF`는
  정말로 앱 버그 신호다.
- **타인의 친구 목록에서도 `relationshipType`은 "나와 그 사람"의 관계다.**
  목록 주인과의 관계가 아니다. 그래서 타인 목록에도 버튼이 선다 — `NONE`이면
  친구 요청이다. 목록에 **내가 들어 있으면 `null`**이라 버튼을 안 그린다.
- **프로필 공개 범위(`FRIENDS`)로 막히는 경우는 명세에 없다.** No 38은 404만
  적어 둔다. 403이 오면 일반 실패로 처리하고, **백엔드에 물어볼 것**으로
  남긴다.

### 9-2. 내가 정한 것

- **받은 요청 배지는 숫자다.** 프로필을 열 때 `friends`의 첫 페이지
  (`limit=20`)를 받아 `FRIEND_REQUEST_RECEIVED` 개수를 센다. 서버가 받은
  요청을 맨 앞에 두므로 첫 페이지면 충분하고, 20개가 꽉 차면 `20+`로 적는다.
  요청이 20개 넘게 밀린 사람에게 정확한 수는 의미가 없다.
- **`요청됨`은 눌리지 않는다.** 추천 탭에서 요청을 보낸 행은 그 자리에
  남지만 비활성이다. 취소하려면 친구 탭으로 간다 — 추천은 새로 맺는 자리고,
  되돌리는 일은 한 곳에 모은다(§4).
- **친구 수와 배지는 화면을 떠날 때 다시 읽는다.** 친구 화면은 push된
  라우트라 돌아와도 프로필이 저절로 갱신되지 않는다. 친구 화면에서 관계를
  **한 번이라도 바꿨으면** pop할 때 프로필 provider를 무효화한다. 아무것도
  안 바꿨으면 그냥 돌아온다.
- **타인 프로필 화면은 `friend` feature가 갖는다.** `profile`의 repository를
  읽으므로 의존이 `friend → profile` 한 방향으로 생긴다. 역방향을 만들지
  않는다(만들면 Riverpod이 `CircularDependencyError`로 막는다).
- **라우트는 shell 밖으로 push한다.** 설정·프로필 편집과 같다.
  `/profile/friends`와 `/profile/user/:userId`이고, 딥링크 대응을 위해
  `app_routes.dart` 한 곳에만 적는다.
- **검색 입력은 `nickname_field.dart`의 디바운스 선례를 그대로 쓴다.** 최소
  길이는 1자다 — 서버가 부분 일치라 한 글자도 뜻이 있다.
- **빈 상태 공통 위젯을 이번에 만든다.** 와이어프레임 `C4`가 규격을 말하지만
  코드에는 없다. `core/widgets/v2/empty_state.dart`로 만들고 친구·추천·검색
  셋이 쓴다.
- **시안 치수 중 토큰에 없는 것은 토큰을 더한다.** 행 높이 62·아바타 48·버튼
  97×40·테두리 0.6은 `AppSpacing`/`AppRadius` 눈금에 없다. 하드코딩은
  `CLAUDE.md`가 막으므로 친구 화면용 상수를 토큰 파일에 더한다.
- **`friends`의 `reason`을 기다리지 않는다.** 받은 요청 줄의 메타 자리는 비운
  채로 낸다. 필드가 생기면 그 자리만 채운다(§8-1).

### 9-3. 개발자가 정한 것 (2026-10-28)

1. **어휘를 "친구"로 통일한다.** 배포된 팔로우 어휘도 이번에 같이 고친다 —
   `ProfileVisibility.followers` → `.friends`(서버 전송값 `FRIENDS`는 그대로),
   `settingsVisibilityFollowers`("팔로워에게만") → `친구에게만`, 그리고 홈의
   `친구랑 뛰기` → **`초대 러닝`**. 홈 칸이 하는 일은 그대로고 문구만 바뀐다.
2. **타인 프로필을 넣는다.** No 38이 개발완료다. 파일이 늘어 PR은 셋으로
   끊는다(계획 문서 참고) — 어휘 / 친구 기능 / 타인 프로필.

화면·위젯은 import하지 않는다.
