# Contributing — Runiverse Frontend

협업 규칙. 구현 함정은 [`implementation-notes.md`](implementation-notes.md)를 본다.

---

## 브랜치

- 형식: **`<type>/<domain>`**
- 소문자, 단어가 여럿이면 **kebab-case(`-`)**

```text
feat/oauth-login
feat/profile-image
fix/token-refresh
refactor/running-session
docs/websocket-api
chore/project-setup
```

`main`과 `dev`에 직접 커밋·push하지 않는다. 항상 작업 브랜치를 따서 PR로 합친다.

| 브랜치 | 역할 |
|---|---|
| `main` | 출시된 상태. 릴리스할 때만 갱신 |
| `dev` | 통합 브랜치. 작업 브랜치가 모이는 곳 |

---

## 커밋 메시지

```text
<type>: <간단한 설명>

(선택)
본문
```

| Type | 설명 |
|------|------|
| 📍 Feat | 새로운 기능을 추가합니다. |
| 🔨 Fix | 버그를 수정하거나 기존 기능(UI/UX 포함)의 문제를 해결합니다. |
| 📝 Docs | 문서를 추가하거나 수정합니다. |
| 🎨 Style | 코드 포맷, 들여쓰기, 공백 등 스타일을 수정합니다. (기능 변경 없음) |
| 🤖 Refactor | 기능 변경 없이 코드 구조를 개선합니다. |
| ✅ Test | 테스트 코드를 추가하거나 수정합니다. |
| 🚚 Chore | 빌드, 설정, 라이브러리, 개발 환경 등을 변경합니다. |
| ✂️ Remove | 파일 또는 사용하지 않는 코드를 삭제합니다. |
| 🔧 Rename | 파일 또는 폴더의 이름을 변경하거나 이동합니다. |

### 예시

```text
📍 Feat: 카카오 로그인 기능 추가

🔨 Fix: JWT 만료 처리 오류 수정

🤖 Refactor: MatchingService 책임 분리

📝 Docs: WebSocket API 명세서 수정

🚚 Chore: Flutter 프로젝트 초기 세팅
```

### 규칙

- 제목은 `<type>: <간단한 설명>` 형식. 설명은 간결하고 명확하게.
- 하나의 커밋에는 **하나의 논리적인 변경 사항만** 포함한다.
- 추가 설명이 필요한 경우에만 본문(Body)을 작성한다.
- 커밋을 나눌 때 **각 커밋이 그 시점에 빌드되는지** 확인한다.
  예를 들어 `pubspec.yaml`의 `assets:`/`fonts:` 선언은 해당 파일을 추가하는 커밋과 같은 커밋에 넣는다.

## Pull Request

### 열기 전에

- **base는 `dev`.** GitHub가 기본 브랜치(`main`)를 base로 잡아두므로 PR을 열 때마다 확인한다.
- 세 가지를 로컬에서 통과시킨다:
  ```powershell
  fvm dart format lib
  fvm flutter analyze     # 경고 0개
  fvm flutter test
  ```
- 한 PR은 파일 20개 / 500줄을 넘기지 않는다.
  프로젝트 초기 세팅처럼 생성 도구가 만든 파일이 대부분이라 불가피하면, 그 사유를 PR 본문에 적는다.
- 넘겼으면 **커밋 경계에서 쪼갠다.** 쪼갠 것들이 서로 기대면 base를 앞 PR 브랜치로 두고 쌓는다 —
  전부 `dev`에 걸면 앞 PR이 머지되기 전까지 뒤 PR의 diff에 앞 커밋이 섞여 보여서 쪼갠 의미가 없다.
  앞 PR이 머지되면 GitHub가 뒤 PR의 base를 `dev`로 다시 잡아준다.

### 제목

커밋 메시지와 같은 형식이다 — `<type>: <설명>`, type 앞에 이모지.

```text
📍 Feat: 유저 온보딩(프로필 최초 등록) 기능 구현
```

### 본문

아래 틀을 채운다. 해당 없는 절은 지우지 말고 비워둔다 —
빈 `삭제` 절은 "지운 게 없다"는 정보지만, 절이 통째로 없으면 리뷰어는 안 적은 건지 없는 건지 모른다.

````markdown
## ✨ 작업 내용

## 🔍 변경 사항

### 추가

### 수정

### 삭제

## 🧪 테스트

- [ ] 단위 테스트
- [ ] 위젯 테스트
- [ ] 로컬 실행 확인
- [ ] 에뮬레이터 확인

### 테스트 내용

## 📷 실행 결과 (선택)

## 💬 리뷰 포인트

## 🔗 관련 이슈
````

### 각 절에 무엇을 쓰나

| 절 | 쓰는 것 | 쓰지 않는 것 |
|---|---|---|
| ✨ 작업 내용 | **무엇을 왜** 했는지 개조식 2~4줄. 배경과 목적 | 파일 목록 (그건 diff가 보여준다) |
| 🔍 변경 사항 | 추가·수정·삭제로 나눠 **`계층: 내용`** 꼴로 나열 | 커밋 메시지 복붙 |
| 🧪 테스트 | 실제로 돌린 것만 체크. **돌린 명령과 결과 수치**를 함께 적는다 | 돌리지 않은 항목 체크 |
| 📷 실행 결과 | 화면이 바뀌었으면 스크린샷·GIF | — |
| 💬 리뷰 포인트 | 봐줬으면 하는 지점과 **판단이 갈렸던 선택** | "확인 부탁드립니다" 같은 빈 문장 |
| 🔗 관련 이슈 | `#12`, `Closes #12` | — |

**변경 사항은 계층을 앞에 적는다.** `presentation: 프로필 사진 시트 추가`처럼 쓰면
리뷰어가 어느 층을 볼지 먼저 정하고 들어올 수 있다.

**해당 없는 절은 `-` 한 줄을 남긴다.** 절을 통째로 지우면 "없다"인지 "안 적었다"인지
구분되지 않는다. 위젯을 안 만든 PR의 `추가` 절이 그 예다.

**화면 작업은 📷 실행 결과가 사실상 필수다.** 코드만으로는 토큰이 제대로 먹었는지 리뷰어가 알 수 없다.
다크·라이트 두 테마를 함께 올린다.

**💬 리뷰 포인트가 이 템플릿의 핵심이다.** 스스로 확신이 없었던 곳을 적는다.
"이 구조를 유지할지 분리할지 의견 부탁드립니다"처럼 **선택지를 함께 제시**하면 리뷰가 빨라진다.
디자인 확인이 필요한 값(임의로 정한 색·간격)도 여기 적는다.

## 커밋 작성자

**커밋과 PR에 AI 도구를 공동 작성자로 넣지 않는다.** 저장소의 기여자 목록은 사람만 남긴다.

GitHub는 커밋 메시지 끝의 `Co-Authored-By:` 트레일러를 읽어 기여자로 집계한다.
따라서 아래 두 가지를 커밋 메시지·PR 본문에 넣지 않는다.

```text
Co-Authored-By: Claude <noreply@anthropic.com>
🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

Claude Code를 쓴다면 트레일러가 자동으로 붙는다. 설정에서 꺼야 한다.

```json
{
  "includeCoAuthoredBy": false
}
```

`.claude/`는 `.gitignore` 대상이라 이 설정은 저장소로 공유되지 않는다.
**각자 한 번씩 켜야 한다.** 저장소의 `.claude/settings.json` 또는
전 프로젝트에 적용하려면 `~/.claude/settings.json`에 넣는다.

이미 push된 커밋에 트레일러가 들어갔다면 되돌리려면 히스토리를 다시 써야 한다.
공유 브랜치에서는 하지 않고, 그대로 두고 이후 커밋부터 지킨다.

## 커밋하지 않는 것

`.env` · `*.keystore` · `*.jks` · `key.properties` · `google-services.json` · `.fvm/` 내부 · 빌드 산출물

API 키와 시크릿은 코드에 하드코딩하지 않고 `lib/core/config/`의 환경변수로만 다룬다.
소셜 로그인 시크릿은 서버 보관이 원칙이다.
