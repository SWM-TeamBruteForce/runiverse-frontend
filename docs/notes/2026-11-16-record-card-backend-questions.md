### ~~새 질문 10. `routeArt` 정규화의 `cos(위도)` 보정~~ — **철회 (2026-11-24)**

**기기에서 재어 답을 얻었고, 사용자가 보정 없이 가기로 정했습니다. 백엔드에 요청할 것이 없습니다.**

에뮬레이터에 동서 360m · 남북 72m 코스(**실측 비 5.0**)를 주입해 카드를 저장하고, 받은
`routeArt`를 쟀습니다.

```
xSpan=1.0000  ySpan=0.1670  aspect=5.9880
```

| 기준 | 비 |
|---|---|
| 실제 거리(m) — 보정했다면 | 5.00 |
| 도(degree) 그대로 — 보정 안 했다면 | 6.27 |
| **서버가 준 값** | **5.99** |

알게 된 것 둘입니다.

1. **비는 보존하십니다.** 짧은 축이 `0~1`을 다 쓰지 않습니다(0.167) — 축마다 따로 늘리지
   않으셨다는 뜻이고, 앱이 바운딩 박스로 되찾는 값이 **정확합니다.**
2. **`cos(위도)`는 곱하지 않으십니다.** 5.99는 6.27 쪽입니다(차이 4%는 10m 리샘플이
   앞을 다듬은 몫으로 설명됩니다). 5.00이 되려면 가로가 20% 더 길어야 하는데 리샘플로는
   그럴 수 없습니다.

그래서 한국에서 경로가 **동서로 약 1.26배 늘어난 채** 그려집니다. 앱은 좌표도 위도도 받지
않아 고칠 수 없습니다. 다만 **지도가 아니라 그림**이고 늘어나는 비율이 어디서나 같아 카드끼리
견줄 때 어긋나지 않으므로, **그대로 두기로 했습니다**(사용자 결정 2026-11-24).

## 배경

- 기록카드 탭은 지금 `ComingSoonPage`이고, **iOS는 심사 때문에 탭 자체를 숨겨 둔 상태**입니다. 화면이 생기면 되살립니다.
- 백엔드 DB 설계와 AI 입출력 계약은 나와 있고, 3차 API 명세서에 **엔드포인트 6개가 등록돼 있으나 여섯 장 모두 본문(요청·응답 스키마)이 비어 있습니다.**
- 경로 표시 방식이 정해졌습니다 — **지도 배경 없이 선만 그리는 "루트 아트"**입니다. 그래서 절대 좌표가 필요 없고, 정규화 좌표만 받으면 됩니다(1-1번).
- 기획이 확정됐습니다 — 러닝 기록 1건에 활동 유형 1개, 회고글(필수), 사진 최대 5장(장당 캡션, 선택), 공개범위 3단계, **AI 음악 생성 여부도 사용자가 켜고 끕니다.**
- 프론트는 도메인 인터페이스 + Fake 구현으로 먼저 짓고, 명세가 나오면 HTTP 구현체만 갈아끼우는 방식으로 진행합니다.

## 핵심 내용

### 1. 응답 계약 3건 - 가장 급합니다

프론트 설계를 검토하다 **현재 코드로는 불가능한 전제**를 하나 발견했습니다. 아래
첫 항목은 답을 못 받으면 도메인 모델부터 다시 지어야 해서 가장 급합니다.

#### 1-1. 카드 조회 응답에 **정규화 경로 · 지표 · 파티원**이 실려야 합니다

- **기획이 먼저 바뀌었습니다**: 기록카드의 경로는 **지도 위에 긋지 않고 배경 없는
  선 아트로** 그립니다(스트라바 루트 아트와 같은 모양). 지도 배경이 없어 **장소가
  드러나지 않고**, 좌표만 있으면 내 카드든 남의 카드든 같은 길로 그립니다.
- **현재 상태**: `running_record_cards`는 `running_record_id`만 들고 있고, 지표와
  경로는 러닝 쪽에서 가져온다는 가정입니다.
- **그 가정이 앱에서 깨집니다**
  - 앱의 `RunRecordRepository`에는 기록 상세가 없습니다. `byRoom(runningRoomId)`
    하나뿐이고, 주석에 "기록 상세 API는 삭제됐다"고 적혀 있습니다.
  - **`running_record_id` ≠ `running_room_id`** 입니다. 카드가 기록 ID만 들고 있으면
    **방 번호를 알 수 없어** 아무것도 못 가져옵니다.
  - **남의 카드는 두 겹으로 막힙니다.** `split-results`가 "방 참가자가 아니면 403
    (`NOT_ROOM_PLAYER`)"이고, 설령 403을 풀어도 명세가 `routes`를 "**이 구간의 본인
    경로**"로 정의합니다 — 본인 기록이 없으면 **전부 `null`로 옵니다.** 남의 경로를
    주는 API가 아닙니다.
- **요청 내용**: 카드 상세 응답에 아래를 직접 실어 주세요.
  - **정규화한 경로** — bounding box 기준 `0~1` 값. 이렇게 주시면 **절대 좌표가 앱에
    한 번도 내려가지 않아** 공개 카드에서도 위치가 새지 않습니다. 선 아트만 그리므로
    절대 좌표가 필요 없습니다
  - **일시정지로 끊긴 조각별로 갈라서** 주세요. 한 배열로 주면 끊긴 구간을 직선으로
    이어 버립니다. 앱은 `List<List<GeoPoint>>` 형태를 씁니다
  - **200~300점으로 단순화**해 주세요. `split-results`는 10m마다라 5km면 수천 점인데,
    선 아트에는 그만큼이 필요 없습니다
  - 총 거리 · 총 시간 · 평균 페이스
  - 함께 뛴 러너의 닉네임·프로필 사진·색 (상세 하단에 아바타로 그립니다)
- **함께 알려 주세요**: 정규화할 때 **경도에 `cos(위도)`를 곱하는 종횡비 보정까지
  하시는지**. 안 하면 앱이 합니다 — 양쪽이 다 하면 모양이 두 번 찌그러집니다.
- **완료 기준**: 카드 응답만으로 타인의 공개 카드 상세가 그려짐

#### 1-2. 러닝 기록 목록 응답에 **카드 유무**

- **왜**: 카드를 쓸 때 "이미 카드가 있는 기록"에 표시를 붙이고 수정으로 보내야 합니다
  (`unique(running_record_id)`). 지금은 앱이 알 방법이 없습니다.
- **요청 내용**: `GET /users/me/running-records` 응답 항목에 `recordCardId`(없으면
  `null`) 추가. 별도 조회 API를 새로 파는 것보다 쌉니다.

#### 1-3. `GET /users/{userId}/record-cards`의 **조회 단위와 상한**

- **왜**: 기록카드 탭이 월 캘린더라 월 단위 조회를 가정하고 짓고 있습니다. 축소(분기)
  보기에서는 3개월을 봅니다. 프로필 그리드는 최신 몇 장만 필요합니다.
- **요청 내용**: 기간(`from`·`to`)을 받는지 커서인지, 한 번에 받는 상한이 몇인지.
  러닝 기록 목록(19번)은 **최대 31일** 제약이 있는데 카드 쪽도 같은지.
- **목록 응답에 필요한 것**: 카드 ID · 러닝 시작 시각 · 활동 유형 · 공개범위 ·
  **첫 사진 썸네일 키** · **사진이 없으면 그릴 정규화 경로**(칸에 선 아트를 그립니다).
  회고 본문과 지표는 목록에 없어도 됩니다.

### 2. 공개범위 값 `FOLLOWERS` → `FRIENDS` - 값 이름 합의 (CHECK 제약 한 줄)

- **현재 상태**: `constraint ck_record_card_visibility check (visibility in ('PUBLIC', 'FOLLOWERS', 'PRIVATE'))`
- **개선 필요성**: 앱은 팔로우 모델이 아니라 **요청→수락 상호 친구 모델**입니다(`features/friend/`, 프로필의 `친구 N · 받은 요청 N`). `FOLLOWERS`를 그대로 쓰면 "내가 팔로우한 사람"인지 "나를 팔로우한 사람"인지 코드와 화면이 계속 어긋납니다.
- **진짜 묻고 싶은 것**: **서버는 `친구 공개` 카드를 누구에게 보여줄 판정을 어느 테이블로 하나요?** 앱에는 팔로우 관계가 없고 상호 친구만 있습니다. 팔로우 테이블을 새로 둘 계획이 있는지, 친구 관계로 판정할 것인지에 따라 값 이름도 따라갑니다.
- **요청 내용**: 친구 관계로 판정한다면 허용값을 `('PUBLIC', 'FRIENDS', 'PRIVATE')`로
- **기대 효과**: 앱 enum·API·DB가 같은 단어를 씁니다
- **완료 기준**: 판정 기준과 허용값이 명세에 반영

### 3. `activity_type` 허용값 확정 - 3개로 제안 (스키마 변경 아님)

- **현재 상태**: `activity varchar(20) not null`에 **CHECK 제약이 없습니다.** 설계 문서가 "최종 허용값은 별도 합의"로 남겼고, AI 문서에 "예시는 `TRAVEL`이며 `DAILY`, `RACE` 등과 대소문자를 혼용하지 않는다"고만 있습니다.
- **DB 컬럼명은 `activity`, API·AI 필드명은 `activity_type`**입니다. 의도한 것인지 함께 확인 부탁드립니다.
- **요청 내용**: 아래 3개로 확정

  | 화면 표기 | 코드 |
  | --- | --- |
  | 일상 | `DAILY` |
  | 대회 | `RACE` |
  | 여행 | `TRAVEL` |

- **판단 근거**: AI 문서가 이미 쓴 예시값과 같습니다. 새로 지으면 AI 전처리와 S3 경로(`audio/{user_id}/{activity_type}/...`)까지 영향이 갑니다.
- **완료 기준**: 세 값이 DB 제약·API 명세·AI 입력 계약에 동일하게 기재

### 4. 썸네일 키 컬럼 추가 - **유일한 스키마 변경**, 생성은 앱이 합니다

- **현재 상태**: `running_record_card_photos.card_photo_key` **원본 키 하나뿐**이고 파생 썸네일이 없습니다.
- **개선 필요성**
  - 기록카드 탭이 월 캘린더라 **한 화면에 썸네일이 최대 31장**, 축소(분기) 보기에서는 **최대 92장**까지 걸립니다.
  - 프로필 사진에서 **8160×6120** 원본이 올라온 전례가 있습니다. 원본을 그대로 내리면 수십 MB가 됩니다.
- **요청 내용**
  - `running_record_card_photos`에 `card_photo_thumb_key text` 추가
  - 사진 업로드 presigned URL을 **원본·썸네일 2개** 발급
  - 카드 목록 응답에는 썸네일 키(또는 서명 URL)만 포함
- **서버 작업이 적습니다**: 앱이 사진을 9:16으로 크롭하므로 **썸네일(긴 변 320px) 생성·업로드는 프론트가 합니다.** Lambda 같은 이미지 처리 파이프라인을 새로 세우지 않아도 됩니다.
- **완료 기준**: 목록 응답으로 받은 썸네일만으로 캘린더가 그려짐

### 5. 음악 완료를 앱이 어떻게 아는가 - 미정, 결정 필요

- **현재 상태**: `music_generations.status`가 `QUEUED` → `PROCESSING` → `SUCCEEDED`/`FAILED`로 움직이지만, **그 변화를 앱에 알리는 방법이 어느 문서에도 없습니다.**
- **개선 필요성**: SageMaker 기본 처리 제한이 **900초(15분)**, 큐 대기 제한이 **21,600초(6시간)**입니다. 사용자가 화면을 열어 둔 채 기다리는 시간이 아닙니다.
- **요청 내용**: 아래 중 하나로 정해 주세요. 프론트는 **(a) + (b) 조합을 제안**합니다.

  | | 방식 | 프론트 준비 상태 | 비고 |
  | --- | --- | --- | --- |
  | (a) | 생성 완료 시 FCM 푸시 | `firebase_messaging` 이미 사용 중 | 페이로드에 `record_card_id`·`status` 필요 |
  | (b) | 카드 상세 진입·당겨서 새로고침 시 조회 | 추가 작업 없음 | 푸시를 못 받은 경우의 보조 수단 |
  | (c) | 앱이 주기적으로 폴링 | 가능하나 권장하지 않음 | 6시간 대기 가능성이라 호출량이 큽니다 |

- **완료 기준**: (a)면 푸시 페이로드 필드가, (b)면 상태를 담은 카드 조회 응답이 명세에 기재

### 6. 등록된 엔드포인트 6개 - 스키마와 일정, 그리고 빠진 것

- **현재 상태**: 3차 API 명세서 `record-card` 도메인에 **여섯 줄이 등록돼 있습니다.** 다만 **여섯 장 모두 본문이 비어 있고**(요청·응답 스키마 없음), BE·FE 현황도 안 찍혀 있습니다.

  | Method | Endpoint | 설명 |
  | --- | --- | --- |
  | POST | `/api/v1/record-cards` | 기록 카드 작성 요청 |
  | POST | `/api/v1/record-cards/drafts/{recordCardDraftId}/complete` | 기록 카드 생성 확정 |
  | GET | `/api/v1/record-cards/{recordCardId}` | 카드 상세 |
  | PATCH | `/api/v1/record-cards/{recordCardId}` | 카드 수정 |
  | DELETE | `/api/v1/record-cards/{recordCardId}` | 카드 삭제 |
  | GET | `/api/v1/users/{userId}/record-cards` | 기록 카드 모음 |

- **6-1. draft 흐름을 알려 주세요.** 작성이 `POST /record-cards` → `complete` **두 단계**인데, 프론트는 **언제 draft를 만들어야 하는지** 모릅니다. 사진 업로드 때문이라면 "작성 시작 → draft 생성 → 사진 올림 → `complete`" 순서로 보이는데 맞나요? 앱은 지금 **작성 세 화면(기록·회고 → 사진 → 공개범위)을 다 거친 뒤 한 번에 저장**하는 흐름이라, draft를 언제 만드느냐에 따라 화면 순서가 달라집니다. 사용자가 중간에 그만두면 draft는 어떻게 되나요(자동 정리 / 남아 있음)?
- **6-2. 사진 업로드 엔드포인트가 목록에 없습니다.** presigned URL 발급을 `POST /record-cards`가 겸하나요, 별도 엔드포인트가 생기나요?
- **6-3. 음악 관련 엔드포인트가 하나도 없습니다.** 생성 요청·재요청·상태 조회가 필요합니다. 특히 **"음악 생성 없이 카드만 저장"**이 가능해야 합니다 — 사용자가 켜고 끕니다.
- **6-4. 러닝 기록 목록 API**(`GET /users/me/running-records`)가 **`개발전`** 상태라, 카드를 쓸 때 **고를 러닝 기록 자체가 아직 없습니다.** 이 일정도 같이 알려 주세요.
- **완료 기준**: 여섯 엔드포인트의 요청·응답 스키마가 채워지고, 빠진 것(사진·음악)이 추가됨

### 7. 서명 URL 만료 시간 - 값 확인

- **현재 상태**: 백엔드가 "카드 접근 권한을 확인한 뒤 사진 접근 주소를 발급"한다고만 되어 있고 만료 시간이 없습니다.
- **개선 필요성**: 캘린더 한 화면에 썸네일 URL이 최대 92개 실립니다. 스크롤하는 동안 만료되면 **빈 칸이 늘어나는 것으로 보입니다.**
- **요청 내용**: 썸네일·원본·음악별 만료 시간 명시. 썸네일은 **10분 이상**을 희망합니다.
- **프론트가 이미 대비한 것**: 조회할 때마다 서명이 달라져도 같은 사진을 다시 내려받지 않도록, **서명을 뗀 경로를 캐시 키로 쓰는 `ImageProvider`가 이미 있습니다**(`lib/core/widgets/profile_photo_image.dart`). 그대로 재사용합니다.
- **완료 기준**: 만료 시간이 명세에 기재

### 8. 사진 순서를 보존해 주세요 - **대표 사진이 그 순서에 걸립니다**

- **현재 상태**: `running_record_card_photos`에 **정렬 키가 없습니다.** 목록을 어떤 순서로 돌려주는지(입력 순서, `id` 순서) 문서에 없습니다.
- **개선 필요성**: 앱에서 사용자가 **대표 사진을 지정**합니다. 지정은 **그 사진을 목록 맨 앞으로 옮기는 것**이고, 카드의 썸네일은 **첫 번째 사진**입니다. 순서가 보존되지 않으면 **지정한 대표가 저장 후 되돌아갑니다.**
- **요청 내용**
  - 카드 수정(`PUT`)이 받는 사진 목록의 **순서를 그대로 저장**해 주세요. 앱은 "남길 사진 전체"를 보여 줄 순서대로 싣습니다.
  - 카드 조회 응답의 사진도 **같은 순서**로 주세요. 정렬 키(`display_order` 등)를 두시는 쪽이 안전하면 그렇게 해 주셔도 됩니다 — 앱은 **응답 순서를 그대로 믿습니다.**
- **완료 기준**: 2번째 사진을 대표로 올려 저장한 뒤 다시 조회하면 그 사진이 첫 번째로 옵니다.

### 9. 그 밖에 확인할 것

- **회고글 필수 여부**: DB는 `review_text` nullable입니다. **앱은 회고 없이 저장할 수 없게 막습니다.** 서버도 막을지, 앱 규칙으로만 둘지 정해 주세요.
- **사진 장수 상한**: DB에 제약이 없습니다. 앱은 **최대 5장**으로 정했습니다(기본 음악 1곡 + 사진 음악 5곡 = 6곡). 서버에서도 같은 값으로 막아 주시면 좋겠습니다.
- **카드 게시 시점**: 설계 문서에 "카드 게시를 음악 완료 이후로 제한할지는 협의"로 남아 있습니다. **프론트는 제한하지 않는 쪽으로 만들었습니다** — 음악이 실패해도 글과 사진은 보입니다.

## 영향 및 주의사항

- **1-1번은 "확인"이 아니라 설계 전제의 문제입니다.** 카드가 경로·지표를 품지 않으면 **타인의 공개 카드 상세를 그릴 방법이 없습니다**(403이고, 403을 풀어도 `routes`가 `null`). 공개범위 기능 자체가 반쪽이 됩니다.
- **정규화 좌표로 주시면 프론트 요구가 줄어듭니다.** 절대 좌표를 안 받으므로 `runningRoomId`도, `split-results` 호출도 필요 없습니다.
- **스키마가 바뀌는 것은 4번(썸네일 컬럼)뿐**입니다. 2번은 CHECK 제약의 허용값, 3번은 제약조차 없는 값 합의입니다.
- **DB 설계가 아직 실제 적용 전 초안**이라 지금 고치면 마이그레이션이 없습니다. 적용 후면 2·4번 모두 마이그레이션이 붙습니다.
- **3번(`activity_type`)은 S3 경로에 들어갑니다**(`audio/{user_id}/{activity_type}/{record_card_id}/...`). 나중에 바꾸면 이미 생성된 음악 파일 경로와 어긋납니다.
- **4번을 안 하면** 캘린더가 원본 사진 수십 장을 내려받아 느려지고 데이터도 많이 씁니다. 기능은 동작하지만 쓸 만하지 않습니다.
- 2~4번이 늦어져도 프론트는 **화면 작업을 계속합니다.** 공개범위 라벨·활동 유형 코드·썸네일 주소만 나중에 채우면 되는 구조로 짓고 있습니다.
- 5번이 정해지지 않으면 **음악 상태가 갱신되지 않습니다.** 카드 자체는 만들어지고 보이므로 치명적이지는 않습니다.

## 팀원 확인 사항

- **담당**
  - 백엔드: 전부
  - AI: 3번(활동 유형 코드가 전처리·S3 경로에 쓰입니다)
- **요청 사항**
  - **1: 카드 응답에 실을 것 확정** — 정규화 경로(조각별·단순화·종횡비 보정 주체)·지표·파티원, 기록 목록의 `recordCardId`, 카드 모음 조회 단위·상한
  - 2: `친구 공개` 판정 기준(친구 관계 / 팔로우)과 값 이름
  - 3: 세 값 확정 + `activity` / `activity_type` 이름 차이 확인
  - 4: 컬럼 추가 가능 여부와 적용 시점
  - 5: FCM / 조회 / 폴링 중 하나 결정
  - 6: **draft 흐름** · 사진 업로드 엔드포인트 · **음악 엔드포인트(생성 없이 저장 포함)** · 여섯 엔드포인트 스키마 일정 + 러닝 기록 목록 API 일정
  - 7 · 8: 값 확인
- **완료 기준**: 8개 항목이 모두 결정되고, 결정된 내용이 API 명세서에 반영되면 프론트가 Fake 구현체를 HTTP 구현체로 교체합니다.
