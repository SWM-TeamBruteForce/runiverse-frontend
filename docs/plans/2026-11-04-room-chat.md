# 대기방 채팅 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 출발 전 대기방에서 파티원과 짧은 메시지를 주고받는 화면을, 서버 없이
가짜 저장소로 동작하는 상태까지 만든다.

**Architecture:** `lib/features/chat/`를 새로 만든다. 화면은 `ChatRepository`만
알고, 이번에 끼우는 구현은 `FakeChatRepository` 하나다. 발신자의 이름·사진은
메시지가 들고 있지 않고 화면이 `room.players`에서 찾는다. `chatProvider`는
`matchRoomProvider`를 **듣지 않고**, 방 번호와 파티원 명단을 화면에서 받는다.

**Tech Stack:** Flutter · Riverpod 3 (`Notifier`) · go_router · `dart:async`.
**새 패키지를 넣지 않는다.**

**Spec:** `docs/specs/2026-11-04-room-chat-design.md`

- `presentation → domain ← data`. presentation은 data를 import하지 않는다

- 아이콘: 이 화면은 v2다. **Lucide를 들이지 않는다.** 쓰는 것은 PNG 두 개뿐
- 화면은 **loading / data / error 3분기**와 **empty**를 모두 그린다. 다크·라이트 둘 다
- `fvm flutter analyze` 경고 0개
- 한 PR 20파일 / 500줄 → **Task 1~3을 PR 하나, Task 4~5를 PR 하나로 올린다**

## Review Focus

명세가 전제하지만 어느 작업의 테스트도 저절로 덮지 않는 것들. 각 줄의 테스트를
괄호 안 작업에 넣어 뒀다.

1. **채팅을 열어 둔 채 방이 죽거나 출발 시각이 닥치는 경로** — 채팅이 먼저 닫히고
   기존 이동이 일어나야 한다. 안 그러면 죽은 방에 사람이 남거나 카운트다운이
   채팅을 갈아치운다 (Task 5)
2. **명단에 없는 `senderUserId`** — 나갔거나 탈퇴한 사람의 메시지. `탈퇴한 사용자`로
   떨어지고 색은 팔레트 끝 색이어야 한다 (Task 4)
3. **공백·개행만 있는 전송** — 아무 일도 일어나지 않아야 한다 (Task 3)
4. **파티원이 나 하나뿐인 방** — 버튼은 숨지만 provider는 붙어 있다. 제목 조립과
   안 읽은 수가 터지지 않아야 한다 (Task 2·3)
5. **아주 긴 닉네임과 아주 긴 한 줄 메시지** — 제목이 두 줄로 나뉜 이유가 이것이고,
   버블은 줄바꿈으로 받아야 한다 (Task 4)

class ChatRoomSeed {

class ChatException implements Exception { const ChatException(); }

abstract interface class ChatRepository {
